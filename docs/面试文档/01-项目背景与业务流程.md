## 一、项目背景

### 1.1 业务痛点与系统定位

跨境电商卖家通常在 **多平台（Amazon / eBay / Shopify / TikTok 等）、多店铺、多仓库（国内仓 / 海外仓 / FBA）** 下经营。订单、库存、采购、售后往往散落在不同工具里，数据不同步会带来三个典型问题：

- **超卖**：库存被多个平台订单重复占用，实际没货却继续卖；
- **缺货与补货滞后**：看不到全局可用库存，热销 SKU 断货才补；
- **对账困难**：收款、退款、平台费用、采购付款口径割裂，算不清利润。

本系统定位为**面向跨境电商卖家的业财一体 ERP 底座**，先把「商品 → 订单 → 仓储 → 采购」这条最核心的经营链路在系统里打通，让库存、单据、流水可追溯、可核算。

### 1.2 技术栈

| 层 | 选型 | 说明 |
|---|---|---|
| 后端 | FastAPI（Python 异步）+ SQLAlchemy + Alembic | 异步框架，ORM 建模，Alembic 做数据库版本化迁移 |
| 数据库 | PostgreSQL 15（本机 Docker） | 关系型，事务与行锁支撑库存一致性 |
| 前端 | Vite + React + TypeScript + Ant Design | 组件化后台，参考领星（跨境 ERP）风格 |
| 鉴权 | 自研 RBAC + Bearer Token | 角色管功能权限，账号绑定店铺/仓库数据范围 |
| 审计 | 业务变更与审计日志同事务落库 | 关键动作可追溯，不记密码/密钥 |

### 1.3 架构风格

采用 **模块化单体（Modular Monolith）**：一个前端、一个后端、一个数据库，但代码内部按业务域（ERP / OMS / WMS / SCM）清晰分层、各管各的数据，模块间通过服务接口协作，而不是各自独立部署的微服务。一期先求「业务跑通 + 数据一致」，把分布式复杂度往后放。

### 1.4 模块划分（一期已实现四大模块）

| 模块 | 业务归属 | 一期负责的数据 |
|---|---|---|
| **ERP** | 企业资源基础 | 商品 / SKU、店铺、仓库、供应商、币种 / 单位、账号角色权限、操作日志 |
| **OMS** | 订单管理 | 销售订单、明细、付款记录、售后申请、订单状态机 |
| **WMS** | 仓储管理 | 库存余额、预留、库存流水、入库单、出库单、盘点 |
| **SCM** | 供应链管理 | 采购单、供货信息、分批收货、补货建议 |

> 业务规划上还有「客户与客服、售后、财务与经营分析、AI 工作台」四个模块（八模块规划），其中客服工单、轻量 CRM、分币种财务对账、AI 助手已落地轻量版，但一期主线是上面四大模块。

### 1.5 一期范围边界（面试常问「你做了什么 / 没做什么」）

**已做**：基础资料 + 两条主链路（销售发货、采购补货）+ 权限 / 审计 + 并发库存控制 + 演示数据。

**明确未做（体现边界意识）**：
- 真实平台拉单（只实现了 `mock` 适配器，其余渠道抛 `NotImplementedError`，不伪造成功）；
- 物流商接口、支付真实退款；
- 多币种汇兑核算、完整财务；
- AI 助手完整版（当前是本地关键词检索 + 人工审核草稿）。

## 二、业务流程

系统一期打通了 **两条主链路**，所有面试技术亮点（并发、幂等、状态机、金额精度）都挂在它俩身上。

### 2.1 销售发货主链路（OMS ↔ WMS 协作）

**订单状态机：**

```
draft（待审核）
   │  approve
   ▼
approved（已审核）
   │  shipment-request（申请发货）
   ▼
shipping_requested（已预留·待拣货）
   │  confirm-ship（确认出库）
   ▼
fulfilled（已发货）

任意阶段 cancel → cancelled（取消须填原因；shipping_requested 取消会释放预留）
```

**端到端步骤：**

1. **商品建档（ERP）**：建商品 → 派生 SKU，绑定计量单位、币种；一个商品可有多个 SKU（如黑白两款保温杯）。
2. **订单录入（OMS）**：手工建单或批量导入。**幂等去重**用 `(shop_id, source_channel, source_order_no)` 唯一键，同店铺同渠道同单号重复导入只生成一笔，错误行返回行号 + 原因。金额按行计算 `行金额 = 数量 × 单价 − 行优惠`，订单总额 = 各行之和，统一 `Numeric(12,2)`，币种必须与店铺一致。
3. **审核（OMS）**：`draft → approved`；取消必须填原因。
4. **发货申请（OMS → WMS）**：WMS 用 `SELECT … FOR UPDATE` **行锁**检查可售库存，不足则整单失败并回滚；成功则创建出库单并 **预留（reserved +）**。
5. **拣货出库确认（WMS）**：扣减在库与预留（`on_hand −`、`reserved −`），写 `outbound` 流水，订单 → `fulfilled`，回传实际发货数量给 OMS。
6. **取消处理**：`shipping_requested` 阶段取消，自动释放预留，避免库存被「幽灵占用」。
7. **售后（OMS）**：退货 / 退款分别记录，已出库订单进入售后流程（一期不调真实支付退款）。

### 2.2 采购补货主链路（SCM ↔ WMS 协作）

**端到端步骤：**

1. **补货建议（SCM）**：基于「销量窗口、采购交期、安全库存、有效库存、有效在途」算出建议数量；**可售已扣除预留的不再重复扣减**；建议可追溯公式与输入，人工调整保留理由。
2. **人工审核转采购（SCM）**：建议 → 采购草稿。**同一建议重复提交不生成重复采购草稿**。
3. **采购（SCM）**：采购单 `draft → submitted → approved → 分批收货 → closed`；已审批单改明细须走**采购变更**重新审核。
4. **分批收货（SCM → WMS）**：到货通知后分批收货（如 10 件分 4 + 6），**实收 / 合格 / 不合格分别记录，只有合格数计入可售**；重复回执不重复收货。
5. **入库（WMS）**：收货确认后增加在库（`on_hand +`）。
6. **采购进度更新（SCM）**：未到数量按批次递减至 0，单据与历史收货记录可追溯。

### 2.3 库存口径（面试核心亮点）

- **在库 on_hand**：仓库实际物理数量。
- **预留 reserved**：已被订单锁定、但尚未出库的数量。
- **可售 available = on_hand − reserved**。
- **并发安全**：所有库存变动都在数据库事务内用 `SELECT … FOR UPDATE` 锁住库存行，防止两个订单同时抢占同一批库存导致**超卖**。
- **防重复**：重复入库、重复出库、重复确认发货均不重复累计（靠出库单状态校验）。
- **盘点**：直接改在库数量，写 `adjust` 流水并保留原因，全程可追溯。

## 三、技术架构（配合图理解）

系统纵向分四层，横向按业务域切分：

- **接入层**：React 前端（Ant Design），通过 Bearer Token 调 `/api/v1/*`。
- **网关 / 鉴权层**：统一登录、RBAC 权限校验、数据范围（shop_scope / warehouse_scope）过滤。**每次请求实时读角色与范围，撤权无需等 Token 过期**。
- **业务模块层**：ERP / OMS / WMS / SCM 四个域，各自维护自己的数据，跨域通过服务方法协作（如 OMS 调 WMS 预留，SCM 通知 WMS 收货）。
- **数据层**：PostgreSQL，统一 Alembic 迁移；金额 / 数量用精确类型，库存一致性靠事务 + 行锁。

## 四、面试可讲的「记忆点」（建议熟记）

1. **一句话定位**：「一个用 AI 连续开发、模块化单体架构的跨境电商 ERP，一期打通了销售发货和采购补货两条主链路，重点解决了多仓多店下的库存超卖和补货滞后问题。」
2. **最难的技术点**：库存并发超卖 —— 用事务 + `SELECT FOR UPDATE` 行锁，把「可售 = 在库 − 预留」这个口径落到数据库约束层面。
3. **最能体现工程素养的设计**：幂等（订单唯一键）、状态机（订单生命周期）、金额精度（Numeric 不跨币种汇总）、审计同事务、权限后端强制校验（不靠前端隐藏按钮）。
4. **边界意识**：平台拉单只做 mock、不伪造成功；明确划出一期不做汇兑 / 完整财务 / 真实支付。
