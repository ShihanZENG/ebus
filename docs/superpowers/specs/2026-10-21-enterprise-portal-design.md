# 企业工作区门户设计

## 意图

依据 CommerceOS 企业经营管理端 PRD 的 G1，交付员工统一入口，使用户进入其已获授权的 ERP 和 AI Operations 工作区。已有 ERP 与 OMS 页面及数据服务继续作为各自系统的权威来源；门户负责入口发现、授权反馈和安全跳转，不复制业务数据。

## 目标

- 登录后进入 `/workspace`，由服务端会话和角色权限生成可用工作区列表。
- 未授权的工作区不出现在入口；直接请求工作区列表仍由后端鉴权。
- ERP、AI 工作区复用现有 ERP 前端页面和 API；OMS 在独立身份授权接入前保持不可点击。
- 门户说明 OMS 的独立身份边界；工作区入口不可被 URL 参数扩大权限。
- 保留现有业务路由，允许门户进入相应的现有页面。

## 非目标

- 本阶段不实现 SSO、ERP↔OMS 写主映射、同步/对账、统一 AI Run 编排、统一提案审批或外部平台写入。
- 不将 OMS 与 ERP 的身份、数据库或业务状态合并；不从 ERP 角色推断 OMS 访问权。
- 不把未接通数据源标记成实时数据。

## 设计

后端新增认证保护的门户工作区只读接口。它从当前会话加载角色，仅按服务端角色权限返回工作区 ID、名称、应用入口、深链和身份提示；管理员可见全部 ERP/AI 入口，普通用户只见其实际具备相应读取能力的工作区。ERP/AI 的深链使用现有本地路由。OMS 身份尚未与 ERP 建立授权映射，因此始终以不可点击状态呈现，不将 ERP 权限当成 OMS 授权。

前端新增独立 `/workspace` 页面。登录成功及根路径导航到门户。门户显示服务端返回的卡片，加载、空、失败和不可访问状态均有明确反馈。选择卡片时仅导航到服务端返回的已知深链；不根据 URL 参数计算权限。保留现有 ERP 页面路由和菜单，避免本阶段大规模迁移。

权限策略：ERP 卡片要求角色具备至少一个 ERP 业务读取权限；AI 卡片要求 `assistant:read` 或 `purchase_agent:read`；管理员拥有 ERP/AI 入口。OMS 在权限映射可验证之前显示为不可用状态。

## 约束与后续

- API 使用现有 FastAPI、SQLAlchemy 会话与 `/api/v1` 前缀，不新增数据库表或迁移。
- 前端使用现有 React、React Router、Ant Design 和 request 客户端。
- 后续 G2/G3/G4 分别单独设计 AI 纵切、跨域诊断与 OMS 对账，沿用本门户的工作区 ID 和清晰系统边界。
- PRD G0 的 B/A/O/P 全量实现状态清单及证据台账未纳入本阶段，须在进入 G2 前完成。
- PRD 中的店铺/站点上下文传播只有在各业务 API 都执行服务端范围校验后再接入；不得只靠前端全局筛选宣称已完成行级授权。
