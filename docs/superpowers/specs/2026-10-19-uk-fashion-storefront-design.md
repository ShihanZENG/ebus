# 织间｜英国女装商城与 ERP 设计

> 已被新的项目定位替代：见 `2026-10-19-ai-commerce-portfolio-design.md`。女装稿保留，不再作为当前实施范围；用户当前目标是 AI 应用开发求职与业务闭环。

日期：2026-10-19。阶段：可实施的方案草案 + 浏览器交互设计稿；尚未修改业务代码、数据库或接通真实支付。

## 1. 意图与边界

用户要面向英国卖衣服、借鉴 SHEIN 的购物方式、保留公司信息与有吸引力的品牌故事，并在自己的 ERP 中处理相关业务；当前展示必须中文，公司信息允许模拟，创意和设计选择交给助手。

设计目标：用户能清楚理解“顾客在哪里买、公司如何展示、自己在哪里处理订单”，并给下一步开发留下可执行边界。

技术目标：在隔离演示环境完成商品发布 → 顾客演示下单 → ERP 审核 → 库存预留 → 出库 → 顾客查单。不是本轮已经实现。

不做：真实收款、真实退款、承运商自动面单、自动报税、全品类、积分、直播、复杂优惠、跨仓拆单、多币种、顾客账号体系和真实广告追踪。现有 ERP 的采购/FBA/财务功能保持原样，不为商城重写。

失败标准：只做漂亮页却无订单接入路径；暴露管理员权限；把演示支付当收入；把出库当签收；用不同系统各记一份库存；用虚构主体进行真实交易。

## 2. 助手作出的默认选择

- 品牌：沿用“织间｜把喜欢，穿进今天”，不伪造创始人履历、环保认证、消费者评价或销量。
- 受众假设：英国日常通勤、周末出门的成年女性；这是待验证定位，不是已证明的消费需求。
- 单站、GBP、中文原型；演示配送范围 GB（英格兰/苏格兰/威尔士），暂不涵盖北爱尔兰及离岸地区。
- 首期 10 款、2 色×3 码＝60 SKU；演示价 £19–£49；每款独立尺寸表，不把 S/M/L 直接等同特定 UK 码。
- React + TypeScript 独立顾客前端，复用 FastAPI/PostgreSQL 的领域服务。
- 第一阶段不改变既有库存占用时点；顾客提交的是“待确认的演示订单”，没有收款、没有保证库存。
- 下一步功能联调只写入独立演示数据库，另设演示店铺和仓库。不得默认为现有库可被覆盖或灌入假数据。

## 3. 信息架构：一个顾客站，一个员工后台

```text
顾客站
├─ 商城首页：场景主题、当季选款、清楚的购买入口
├─ 全部服饰：针织/上衣/连衣裙/下装，筛选及排序
├─ 商品详情：图片、版型、尺码、颜色、价格、配送和退换说明
├─ 购物袋 → 结算 → 订单结果 → 订单查询
├─ 品牌故事：沿用已写好的中文品牌叙事
├─ 公司与联系：经营主体、联系渠道、合作入口
└─ 帮助：尺码、配送、退换、条款、隐私

ERP（员工登录）
├─ 现有：商品/SKU、店铺、库存、订单、出库、售后
└─ 新增“独立站运营”
   ├─ 商品发布：关联 SKU、图片、定价、上架/下架
   ├─ 内容管理：品牌故事、公司信息、首页专题
   └─ 业务设置：站点、配送、演示模式、政策版本
```

不把业务设置放进顾客导航。公司与品牌内容共享商城的页眉页脚，初期不做独立集团站；仅管理端可编辑。

## 4. 页面与视觉设计

### 首页

暖白底、深灰正文、酒红强调色，延续已有品牌页；摄影用于营造穿搭场景，商品区域仍以可读的名称、价格和购买操作为主。移动端优先，桌面最大内容宽度约 1240px，交互目标不小于 44px，按钮有键盘焦点。

首屏文案：“把喜欢，穿进今天。”副文案：“从平日的通勤，到临时起意的见面。让每一个普通日子，都有一件想穿出门的衣服。”主按钮“挑选今天的喜欢”，次入口“认识织间”。不把整篇品牌故事塞进首屏。

首屏下方：通勤/周末/轻聚会主题 → 当季选款 → 一件多穿的搭配内容 → 简短品牌故事 → 公司、帮助及政策入口。不使用自动播放、假倒计时或虚假抢购提示。

### 商品详情

左侧图集，右侧依次显示名称、GBP 价格、颜色、尺码、尺寸指南、数量、加入购物袋。移动端改为纵向，关键购买操作在可见位置。

信息包括：真实纤维成分、触感与厚薄（有证据才写）、版型、实测尺寸和测量方法、模特尺码（确有样片才写）、护理建议、配送费用与时效、退换入口。演示数据标识不可隐藏。

缺码禁选；未选规格不能加入；下架或价格变化时重新确认；没有评价就显示无评价，不造五星。AI 概念图标“概念穿搭图，非商品实拍”。

### 购物袋与结算

购物袋可改规格/数量、移除，显示行小计和总计。结算顺序：联系邮箱 → 收件人和地址 → 配送 → 复核金额 → 提交。当前设计稿只用固定虚构收件信息，不采集真实个人信息。

接入版收件字段：姓名、邮箱、地址行1/2、城市、地区、邮编、国家（GB），电话按承运要求处理，不强制无必要数据。GB 配送与区域限制在后端验证，不能仅凭前端国家下拉框判断。

演示版运费 £0、无折扣、无真实税费计算，所有商品价为测试总价。按钮写“提交演示订单（不扣款）”，成功页写“演示订单已收到，等待商家确认库存”。模拟付款状态只能是独立的 `simulated` 标识，不能写入真实支付到账状态。

### 订单查询

显示顾客订单号、购买快照、总额、业务状态和可见物流信息；不显示内部备注、成本、供应商、其他顾客或仓库敏感信息。展示“已出库”而非“已签收”；手工单号注明未接物流轨迹。

### 公司与故事

沿用 `docs/品牌与独立站/织间品牌创作稿.md`；公司样本为“织间服饰（演示）有限公司”、英国伦敦示例街12号、`hello@loomandlane.example`。所有虚构信息明确标识。真实上线必须替换，禁止编注册号、认证和联系电话冒充真实经营者。

## 5. 后端数据边界

复用 Product、SKU、Shop、InventoryBalance、InventoryOwnership、SalesOrder、SalesOrderItem、ShipmentOrder；库存数量以 ERP 为唯一事实来源，不在商城表维护一套手动库存。

新增领域对象（命名可由开发者微调，职责不能省略）：

| 对象 | 必需信息/约束 |
|---|---|
| StorefrontSite | 唯一站点 code、shop_id、GBP 币种、允许仓库、地区、mode=demo、启用状态 |
| StorefrontProduct | site_id+slug 唯一、product_id、展示标题、正文、分类、图集、尺寸表、draft/published/archived、版本 |
| StorefrontVariant | site_id+sku_id 唯一、所属商城商品、颜色尺码展示、Decimal 售价、启用状态 |
| StorefrontContent | 站点、页面键、草稿内容、发布快照/版本；仅白名单结构化字段，不接受任意脚本 |
| StorefrontOrderMeta | 与 SalesOrder 一对一、随机公开订单号、完整收货地址快照、币种、演示标记、访问令牌哈希 |
| CheckoutSubmission | site_id+Idempotency-Key 唯一、请求摘要、order_id、时间；同键不同参数拒绝 |

订单商品快照补充公开标题、颜色尺码、价格和商品版本，后续编辑商品不改变历史订单。现有 SalesOrder 无结构化完整收货地址，不能把地址只拼进 remark。

金额统一后端 Decimal，API 使用如 `"29.00"` 的两位小数字符串与 `currency:"GBP"`。客户端不得提交最终单价、税额、支付成功标记、shop_id、warehouse_id 或订单状态。演示订单的 grand_total 与明细小计一致，真实运费/税额扩展另做方案。

## 6. 公共接口与权限

新增 `/api/storefront/v1` 命名空间，独立响应模型；不要直接返回 `order_snapshot` 或 ORM 全字段。

| 接口 | 契约 |
|---|---|
| GET /site | 当前站点公开内容、GBP、明确的 demo 标识、已发布政策版本 |
| GET /products | 仅发布且启用的商品；分页、类别/尺码筛选、白名单排序 |
| GET /products/{slug} | 规格与售价、尺寸表、可用状态；按店铺+允许仓库计算 |
| POST /checkout | 只收 variant_id、数量、地址与联系、见过的报价/版本，要求 Idempotency-Key；验证后建 draft |
| GET /orders/{public_id} | 必须提供仅能读取该订单的访问令牌；返回脱敏公开订单模型 |

结算必须重新查发布状态、SKU 状态、价格版本及可售量。价格变动返回 409 和新报价，要求用户确认再提交；缺货不创建承诺履约订单。网络失败重试使用同一个幂等键，不重复创建订单。

订单创建和幂等记录在同一事务提交，唯一冲突读回原结果；接入服务复用/抽取现有订单明细校验与计算逻辑，不绕过数据完整性。来源固定 `storefront_demo`，不接收客户端来源。新命名空间由 main 注册；不会把现有受保护的 `/api/v1/orders` 改为匿名。

访客不需要管理员账号。结算生成高熵订单访问凭据，服务端只保存哈希；首次返回后存浏览器 sessionStorage，仅通过 Authorization 请求头传递，不放 URL、日志或分析事件。幂等重试用客户端首次生成并持有的高熵恢复凭据验证后补发轮换令牌，旧令牌失效；不能仅凭 Idempotency-Key 或公开单号恢复访问。客户端须在首次提交前保存恢复凭据；丢失则演示版重新开始，不提供可枚举的查单接口。正式找回/邮件链接属于后续范围。

设置路由需新增明确权限，并遵守已有店铺/仓库范围；保存与发布记录员工审计。公共创建使用专用服务事件，不冒用管理员身份填审计，事件必须脱敏。公开端加请求体/数量上限、限流、分页上限；不以 CORS 代替鉴权。

独立商城 Vite 配置不导入 ERP `demoCredentials.mjs`，不读取 backend/.env。演示环境仅绑定回环地址；真实部署需 HTTPS、密钥管理、个人数据保护、备份及监控专项检查。

## 7. 订单、库存和付款的精确语义

| 事件 | ERP 状态 | 顾客展示 | 库存行为 |
|---|---|---|---|
| 提交演示订单 | draft | 已收到，待确认库存 | 不占用、不扣减 |
| 员工审核并选仓 | approved | 商家处理中，尚未锁定库存 | 不占用、不扣减 |
| 申请发货成功 | shipping_requested | 备货中 | 在事务中预留，生成 picking 出库单 |
| 申请发货缺货 | 保持 approved | 暂缺货，待商家处理 | 整笔回滚，无半笔预留；管理员异常待办 |
| 仓库确认出库 | fulfilled | 已出库 | 扣 on_hand 与 reserved，保存单号 |
| 未出库订单取消 | cancelled | 已取消 | 有预留则释放；不增加实际在库量 |

缺货状态通过 StorefrontOrderMeta 中的 fulfillment_issue 记录给顾客提示，不能伪造一个 ERP 不支持的主状态；成功申请、取消时清除。该失败提示在库存事务回滚之后另行可靠记录，不改变订单主状态。

可售量使用 `inventory_allocation.available`：本店可用专属库存 + 公共可用库存，不包含其他店专属可用量；首期只绑定一个履约仓，避免聚合可售而实际不能单仓发货。SKU 按固定顺序加锁，沿用现有 reserve/finish 服务。

本阶段允许多个待确认草稿竞争最后一件货，但只有成功申请发货的一笔能预留。故**不能宣传“提交即锁库存”或将其用于先付款后发现缺货的真实销售**。下一阶段真实结算的占用/支付/超时机制须单独设计并通过并发测试。

第一阶段不创建真实 PaymentRecord；simulated 仅演示元信息，不能用于财务已收款合计、退款或真实发货授权。专用测试数据库避免演示 SalesOrder 混入正式订单营收汇总。前台每次打开或手动刷新订单页读取 ERP 当前状态；暂不做消息队列、实时推送或物流轨迹自动同步。

在 ERP 现有订单详情页显示结构化收货地址和“演示订单”标识，提供明确演示店铺筛选；库存和出库页沿用现有入口。顾客不能操作审核/出库。演示数据不允许导出到真实履约系统。

## 8. 真实营业前再开启的能力

支付机构选择取决于实际主体和账户资格，本方案不替用户承诺供应商可用。采用托管支付页，不自存卡号；服务端验证签名、金额、币种、订单关联并幂等处理。支付到账、库存占用、订单业务状态分离，设计晚到回调与退款补偿。

发货地、承运商、税费、退货地点尚未知，不能硬编码“英国本地仓”“包税”“次日达”。从中国直发与英国备货两种模式要以真实成本、时效和退款方案比较后再选。

政策内容必须由真实经营主体核验；中文设计不是对英语转化或英国法律适用的判断。具体风险与官方依据见可行性分析。

## 9. 实施顺序与验收

1. 先准备独立演示数据库，复用现有迁移；确认现有 ERP 的商品、订单、预留、出库基础流程可运行。只有新测试库可初始化演示数据。
2. 做一款商品的发布、受限公共查询与独立商城商品页，再扩展至 10 款。商品管理和发布权限检查同时完成。
3. 做购物袋、结算验证、幂等与访客查单，把订单放入演示 ERP；在 ERP 展示地址、来源及演示标记。
4. 接通审核、申请发货、出库、取消和前台状态映射，再做公司内容发布与业务设置。
5. 做最小风险验收，未通过不宣称闭环完成。

验收必须证明：

- 同一商品颜色/尺码映射正确，同一 SKU 价格篡改无效；下架不可再购买。
- 同一次提交重试仅一笔订单；相同键不同参数被拒绝，不能通过幂等键拿走别人的订单。
- A 顾客令牌不能查 B 订单，公开接口不泄露后台字段或管理员凭据。
- 最后一件库存两笔申请发货仅一笔成功；多 SKU 缺货整笔回滚；不能占用其他店专属库存。使用 PostgreSQL 验证行锁，不能拿 SQLite 测试代替并发保证。
- 审核不占货，申请才预留；取消释放一次；重复出库不重复扣库存。
- 售价变化、无货、断网重试、空购物袋、无效地址均有明确反馈。
- 真实支付和退款没有发生；演示不进入正式数据库和报表。
- 出库后前台可读到同一订单单号和状态，不显示已签收。
- 390px 移动端与桌面无关键内容遮挡；键盘可选规格、关闭弹窗并回到触发按钮。

当前可点击设计稿只展示交互与状态语义，浏览器内存模拟，刷新即重置；不调用 ERP 接口、不保存个人信息、不是以上联调验收证据。
