# 跨境电商 ERP 系统 · 部署说明

本文面向"换一台新机器，从零把系统跑起来"的人，按**数据库 → 后端环境 → 迁移 → 初始化 → 启后端 → 启前端**六步给出可执行命令。

分工说明：`backend/README.md` 讲的是"日常怎么跑起来 + 接口怎么用"，本文讲的是"新机器怎么装 + 每一步怎么验证 + 出问题怎么排查"。两者不冲突，日常启动看 `backend/README.md`，换机器或排障看本文。

## 1. 前置条件

1. **Docker Desktop**（含 Compose v2）。验证：`docker -v`、`docker compose version`。
2. **Python 3.11 及以上**（本机实测 3.13.5）。Windows 上需勾选 "Add python.exe to PATH"，或直接用完整路径调用。
3. **Node.js 18 及以上**（本机实测 22.22.2）+ npm。验证：`node -v`、`npm -v`。
4. 磁盘剩余空间建议 2 GB 以上（Docker 镜像 + `node_modules`）。
5. 本机 **15432 / 18080 / 15173** 三个端口未被占用（占用处理见第 8 节）。

不需要单独安装 PostgreSQL——数据库跑在 Docker 容器里。

## 3. 第一步：启动数据库

数据库由 `backend/compose.yaml` 定义：镜像 `postgres:15-alpine`，宿主端口 `127.0.0.1:15432` 映射到容器 5432，数据落在 Docker 卷 `erp_data`（普通 `stop`/`start` 不清空数据）。

```powershell
cd backend
docker compose -p crossborder-erp up -d db
```

- `-p crossborder-erp` 指定项目名，容器名因此是 `crossborder-erp-db-1`。**换机器请保持这个参数一致**，否则会新建一个空库容器。
- `compose.yaml` 里的库名/用户名/密码取自 `.env` 的 `POSTGRES_DB` / `POSTGRES_USER` / `POSTGRES_PASSWORD`，所以**必须先有 `.env`**（见第 4 步）。新机器上若 `.env` 还没建，先做第 4 步再回来执行本命令。

确认起来了（两条都要看）：

```powershell
docker ps --format "table {{.Names}}\t{{.Image}}\t{{.Status}}\t{{.Ports}}"
docker compose -p crossborder-erp ps
```

正常应看到：

```text
NAMES                  IMAGE                STATUS                 PORTS
crossborder-erp-db-1   postgres:15-alpine   Up 3 hours (healthy)   127.0.0.1:15432->5432/tcp
```

关键是 **`STATUS` 必须带 `(healthy)`**。`compose.yaml` 内置了 `pg_isready` 健康检查（3 秒一次、最多 20 次），首次拉取镜像需要几十秒，请等到出现 `healthy` 再执行迁移。一直不健康时看日志：

```powershell
docker compose -p crossborder-erp logs db
docker logs crossborder-erp-db-1
```

停止/启动/彻底删除（**带 `-v` 会连数据卷一起删，数据不可恢复，慎用**）：

```powershell
docker compose -p crossborder-erp stop db      # 停，数据在
docker compose -p crossborder-erp start db     # 再起，数据在
docker compose -p crossborder-erp down         # 删容器，保留 erp_data 卷
docker compose -p crossborder-erp down -v      # 连 erp_data 卷一起删，慎用
```

## 4. 第二步：后端环境与 `.env`

### 4.1 创建虚拟环境并安装依赖

```powershell
cd backend
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

`requirements.txt` 锁定版本：fastapi 0.128.0、uvicorn 0.52.1、SQLAlchemy 2.0.52、alembic 1.19.1、pydantic 2.13.4、psycopg[binary] 3.2.13、httpx 0.28.1、pytest 8.3.4、tzdata 2025.2。

验证安装结果：

```powershell
.\.venv\Scripts\python.exe -m pip list
```

> 注意：本机 `.venv` 复用了本机已有的 Python 依赖并补装了 PostgreSQL 驱动，因此 `pip list` 里可能比 `requirements.txt` 多出包。这不影响运行，换机器按 `requirements.txt` 装即可。

### 4.2 配置 `.env`

从模板复制（**不要**把 `.env` 提交到仓库或粘贴到聊天/工单里）：

```powershell
Copy-Item .env.example .env
```

`backend/.env` 共 7 个键，逐项说明如下。**本文不写任何真实密码，请从本机 `backend/.env` 取值**：

| 键 | 说明 | 示例（占位符） |
| --- | --- | --- |
| `DATABASE_URL` | SQLAlchemy 连接串。格式 `postgresql+psycopg://<用户>:<密码>@127.0.0.1:15432/<库名>`。**必须与下面三个 POSTGRES_* 一致**，否则后端连不上容器里的库 | `postgresql+psycopg://erp:<你的库密码>@127.0.0.1:15432/erp` |
| `POSTGRES_DB` | 容器初始化时创建的库名 | `erp` |
| `POSTGRES_USER` | 数据库超级用户名 | `erp` |
| `POSTGRES_PASSWORD` | 数据库密码。**换机器请换成你自己生成的强密码**，并同步改 `DATABASE_URL` 里的密码 | `<自行生成的强密码>` |
| `ERP_ADMIN_USERNAME` | 初始化时创建的**管理员登录账号** | `admin` |
| `ERP_ADMIN_PASSWORD` | 管理员初始密码，**至少 8 位**（`app/bootstrap.py` 会校验长度，不足 8 位直接报错） | `<至少8位的强密码>` |
| `ERP_SESSION_HOURS` | 登录会话有效小时数，缺省 8 | `8` |

要点：

- 密码里若含 `@ : / #` 等字符，在 `DATABASE_URL` 中需要做 URL 转义，否则连接串会被截断。本机现网密码含 `-` 和 `_`，无需转义。
- 换机器时"库密码"和"管理员密码"建议各自独立生成，不要复用旧值。
- 仅测试用得到 `TEST_DATABASE_URL`（`backend/tests/test_erp.py` 读取）：不设置时测试跑临时 SQLite，不碰演示库；设置了则连 PostgreSQL 并在随机隔离 schema 中跑。**不要把日常库当成测试目标**。

### 4.3 `.env` 是怎么被读到的

`app/config.py` 的 `load_env()` 在导入时读取 `backend/.env`，用 `os.environ.setdefault` 写入进程环境变量（即：**系统已存在的同名环境变量优先级更高**，`.env` 只作兜底）。`alembic` 的 `migrations/env.py` 会 `import app.config`，所以**迁移命令也会自动吃到 `.env`，不需要额外 export**。

## 5. 第三步：数据库迁移

迁移脚本在 `backend/migrations/versions/`，当前 4 个版本、head 为 `0004`：

```text
0001  ERP 身份与基础资料
0002  OMS 销售订单、明细、付款、售后
0003  WMS 库存余额、流水、入库单、出库单
0004  SCM 供货价、采购单、收货、补货建议
```

### 5.1 升到最新

```powershell
cd backend
.\.venv\Scripts\python.exe -m alembic upgrade head
```

### 5.2 确认当前版本

```powershell
.\.venv\Scripts\python.exe -m alembic current     # 预期输出：0004 (head)
.\.venv\Scripts\python.exe -m alembic history     # 查看完整版本链
```

`alembic history` 的正常输出：

```text
0003 -> 0004 (head), SCM supplier SKUs, purchase orders, receipts and replenishment suggestions.
0002 -> 0003, WMS inventory balances, transactions, inbound and shipment orders.
0001 -> 0002, OMS sales orders, items, payments and after-sales.
<base> -> 0001, ERP identity and master data foundation.
```

还可以用 `alembic check` 确认"模型定义与迁移是否一致"（无输出变更即一致）：

```powershell
.\.venv\Scripts\python.exe -m alembic check       # 正常：No new upgrade operations detected.
```

### 5.3 回滚一个版本（有风险，谨慎）

```powershell
.\.venv\Scripts\python.exe -m alembic downgrade -1        # 回退一步，0004 -> 0003
.\.venv\Scripts\python.exe -m alembic downgrade 0003      # 回退到指定版本
```

- 回滚会**真实删除表/列**，执行前务必备份（`pg_dump` 或复制数据卷）。
- 回滚只会改结构，不负责把业务数据变回去。
- 生产环境不要直接 downgrade，先演练。

## 6. 第四步：初始化（管理员账号 + 演示数据）

### 6.1 管理员账号从哪来

管理员**不是**手写在 SQL 里的，而是由 `backend/app/bootstrap.py` 生成：读取 `.env` 的 `ERP_ADMIN_USERNAME` / `ERP_ADMIN_PASSWORD`，创建 `admin` 角色（全权限）、`viewer` 只读角色，以及管理员账号（密码用随机盐 PBKDF2-SHA256 存哈希，不明文落库）。同时补两条基础字典：单位 `PCS`、币种 `CNY`/`USD`。

```powershell
cd backend
.\.venv\Scripts\python.exe -m app.bootstrap          # 仅管理员、角色、基础字典
.\.venv\Scripts\python.exe -m app.bootstrap --demo   # 追加合成演示商品/店铺/仓库/供应商
```

脚本是**幂等**的：已存在的记录保持原值，已存在的账号**不会被重置密码**。正常输出：

```text
初始化完成。已有记录与密码保持原值；凭据不输出。
```

密码不足 8 位会报：`初始化需 ERP_ADMIN_USERNAME 与至少8字符的 ERP_ADMIN_PASSWORD`。改完 `.env` 重跑即可（改密码后需重新执行才会生效到新库；已有账号请用管理员在"账号与角色"页重置密码）。

### 6.2 灌入演示数据

`backend/scripts/seed_demo.py` **走真实 HTTP 接口**写入（不是直连数据库），因此会完整经过后端校验、库存事务与状态机。内容约：8 商品 / 17 SKU / 5 店铺 / 6 仓库 / 15 张覆盖各状态的订单 / 7 张采购单（含分批收货）/ 6 条补货建议 / 500+ 库存流水。脚本幂等，可重复执行。

**前置条件：后端必须已在 18080 运行**，且已完成第 5、6.1 步。

```powershell
cd backend
.\.venv\Scripts\python.exe scripts/seed_demo.py
```

演示数据只用于本地开发/演示库，不要灌入生产库。


### 8.1 生产构建与 `/api` 代理

- `npm run build` 只产出静态文件（`frontend/dist`），**不提供 API**。
- 前端所有请求都走相对路径 `/api/v1`（见 `frontend/src/api/client.ts` 的 `BASE = '/api/v1'`），因此**部署静态产物时必须由 Web 服务器把 `/api` 反向代理到后端 18080**，例如 Nginx：

  ```nginx
  location / {
      root <站点目录>;
      try_files $uri $uri/ /index.html;
  }
  location /api/ {
      proxy_pass http://127.0.0.1:18080;
      proxy_set_header Host $host;
  }
  ```

- dev 模式下同样的代理由 Vite 承担（见下），所以页面上的登录和取数都是真实调用后端。

### 8.2 代理说明（`frontend/vite.config.ts`）

```ts
server: {
  host: '127.0.0.1',
  port: 15173,
  proxy: { '/api': { target: 'http://127.0.0.1:18080', changeOrigin: true } },
}
```

即：浏览器只访问 15173，`/api/**` 由 Vite 转发到 18080，因此**不需要后端开 CORS**（后端也确实没有注册 `CORSMiddleware`）。改后端端口或换机器部署时，两处（这里 + Nginx）都要同步改。

## 10. 常见问题排查

### 10.1 端口被占用

现象：后端报 `Address already in use`；或 Vite 提示 `Port 15173 is in use, trying another one...`（Vite 会自动顺延端口，导致前端代理后的页面打不开预期端口）。

```powershell
netstat -ano | findstr ":18080 :15173 :15432"
```

找到最后一列的 PID，再确认进程后结束它：

```powershell
tasklist /FI "PID eq <PID>"
taskkill /PID <PID> /F        # 确认是无关进程后再执行
```

15432 被占用时，通常是本机已有 PostgreSQL：要么停掉它，要么改 `compose.yaml` 的宿主端口映射（改完必须同步改 `.env` 的 `DATABASE_URL`）。

### 10.2 数据库连接失败

按顺序自查：

1. 容器是否 `healthy`：`docker compose -p crossborder-erp ps`。没起来就看 `docker logs crossborder-erp-db-1`。
2. `.env` 里的 `DATABASE_URL` 主机/端口是不是 `127.0.0.1:15432`、库名是不是 `POSTGRES_DB`、用户名密码是否与 `POSTGRES_USER`/`POSTGRES_PASSWORD` 一致。
3. **改过 `POSTGRES_PASSWORD` 但库是旧的**：容器内 Postgres 只在卷为空时初始化账号，改密码不会自动生效。需要改库内密码（`docker exec -it crossborder-erp-db-1 psql -U erp -d erp` 后 `ALTER USER erp PASSWORD '...'`），或删卷重建（会丢数据）。
4. 密码含特殊字符未做 URL 转义，导致连接串被截断。
5. `/ready` 返回 503 但 `/health` 正常 → 数据库可达但迁移表/用户表缺失，回到第 5 步跑 `alembic upgrade head` 和第 6.1 步跑 `bootstrap`。

### 10.3 迁移不同步

- `alembic current` 不是 `0004 (head)` → 跑 `alembic upgrade head`。
- 报 `Can't locate revision identified by 'xxxx'` → 本地 `migrations/versions/` 缺少该版本文件（常见于回退分支或漏拉代码），先把代码同步到同一提交再迁移。
- 报 `Target database is not up to date` → 通常是某个版本执行到一半失败，先查 `alembic current` 与 Postgres 报错，修好后重跑；必要时（已备份前提下）`downgrade -1` 再 `upgrade head`。
- `alembic check` 报检测到变更 → 模型与迁移不一致，需要由开发补一条新迁移，不要手改库结构。
- 多机共用同一个库时，迁移只能由一处执行。

### 10.4 Vite 预构建失败 / dev server 启动即崩

`frontend/vite.config.ts` 已把预构建缓存目录从默认的 `node_modules/.vite` 挪到系统临时目录（`os.tmpdir()/crossborder-erp-vite`），原因是本机安全策略会拦截项目内删除操作，导致 Vite 重优化依赖时崩溃。

- 仍失败时，换一个缓存目录：`$env:VITE_CACHE_DIR='C:\Temp\vite-cache'` 后再 `npm run dev`。
- 依赖大改后缓存不干净：`npm run dev -- --force`。
- `npm install` 报网络/权限错误：先 `npm cache verify`，仍不行则删除 `node_modules` 后重装（**本项目在安全策略下不要批量删除文件**，请让工程负责人确认后操作）。

### 10.5 CORS / 前端请求失败

- 后端**未注册** `CORSMiddleware`，跨域直连 18080 会被浏览器拦掉。请务必通过 15173 的 `/api` 代理访问，不要前端直写 `http://127.0.0.1:18080`。
- 代理 502/超时 → 后端没起或不在 18080，先验 `/health`。
- 401 → 未登录或 token 过期（`ERP_SESSION_HOURS`，默认 8 小时）；连续 5 次密码错误会锁定 5 分钟（429）。
- 403 → 当前角色缺权限或店铺/仓库数据范围受限。

### 10.6 登录失败

- 用户名/密码取自 `backend/.env` 的 `ERP_ADMIN_USERNAME` / `ERP_ADMIN_PASSWORD`。改过 `.env` 但库里已有该账号时，bootstrap **不会**覆盖旧密码，需用另一位管理员在"系统 → 账号与角色"重置，或重建库后重新 bootstrap。
- 前端页面密码同样见 `backend/.env`，不要写进工单或截图。

## 11. 安全注意事项

- `backend/.env` 含数据库与管理员明文凭据：**不提交仓库、不粘贴到聊天/工单/截图**。本文一律使用占位符。
- 数据库只绑 `127.0.0.1`，不要改成 `0.0.0.0` 对外暴露。
- 换机器请重新生成库密码与管理员密码，不要复用旧值。
- 接口 token 只在 `/docs` 的 Authorize 中使用，不要外传；退出用 `POST /api/v1/auth/logout`，token 立即失效。
