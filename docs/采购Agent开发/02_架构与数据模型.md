## 1. 总体架构

```text
请求方（用户/后续 AI 总助手）——结构化请求
        │
        ▼
┌────────────────────────────────────────────┐
│ purchase_agent.decide()                     │
│ ① validate_request   请求字段与权限前置校验 │
│ ② validate_evidence  证据采集与校验(读库)   │
│ ③ replenish()        确定性计算(纯函数)     │
│ ④ constraint check   预算/停止条件          │
│ ⑤ create_draft       生成草稿(幂等)         │
│ ⑥ compose_result     组装输出               │
└──────────────┬─────────────────────────────┘
               │ 只读证据查询 / 草稿写入
               ▼
┌────────────────────────────────────────────┐
│ 现有业务层（复用）                          │
│ SKU/Warehouse/Supplier/SupplierSku         │
│ InventoryBalance（本地/FBA）                │
│ PurchasePlan（审批通过后创建）              │
│ AuditLog（审计）                            │
└────────────────────────────────────────────┘
```

架构原则：

1. LLM（未来）负责理解与解释，函数负责确定性计算；本批所有计算为纯函数。
2. 只读证据自动执行；写入（草稿创建、审批、转计划）受权限控制且审批动作只做状态迁移。
3. 证据不足必须 BLOCKED，禁止把 null 当 0、禁止猜测。
4. 每次执行写入 agent_runs / agent_tool_calls，可复算、可审计。

## 2. 数据模型

新增三张表（迁移 `0007_purchase_agent`），沿用 `Record` 基类约定（id、created_at、updated_at）。

### 2.1 agent_runs（Agent 运行记录）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | String(36) PK | UUID |
| case_id | String(64) | 调用方业务标识（可空） |
| sku_id | FK skus.id | 目标 SKU |
| shop_id | FK shops.id nullable | 目标店铺（可空） |
| as_of | DateTime | 业务时点（UTC） |
| status | String(20) | RECEIVED/VALIDATING/READY/CALCULATED/DRAFTED/BLOCKED/CONSTRAINT_CONFLICT/FAILED |
| request_payload | JSON | 请求摘要 |
| result_payload | JSON | 结果摘要（计算、证据、决策） |
| idempotency_key | String(255) | 幂等键（可空） |
| draft_id | FK purchase_agent_drafts.id nullable | 关联草稿 |
| error_message | String(500) | BLOCKED 原因 |

索引：sku_id、shop_id、status、case_id。

### 2.2 agent_tool_calls（工具调用明细）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | String(36) PK | UUID |
| run_id | FK agent_runs.id | 所属运行 |
| tool | String(64) | 工具名（get_inventory/get_supplier_sku/compute/draft 等） |
| params | JSON | 参数摘要 |
| result | JSON | 返回摘要 |
| snapshot_id | String(64) | 快照标识（as_of 派生） |
| status | String(16) | ok/error |
| elapsed_ms | Integer | 耗时（毫秒） |

索引：run_id、tool。

### 2.3 purchase_agent_drafts（采购草稿）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | String(36) PK | UUID |
| draft_no | String(40) unique | 草稿编号 PA-DRAFT-YYYYMMDD-XXXX |
| sku_id | FK skus.id | SKU |
| shop_id | FK shops.id nullable | 店铺 |
| warehouse_id | FK warehouses.id | 目标仓库（本地仓） |
| suggested_qty | Integer | 建议采购量 |
| target_stock | Integer | 目标库存 |
| net_gap | Integer | 净缺口 |
| moq | Integer | 起订量 |
| case_pack | Integer | 箱规 |
| unit_price | Numeric(12,2) | 单价（审批时点） |
| total_amount | Numeric(12,2) | 建议货值 |
| currency_id | FK dictionaries.id | 币种 |
| expected_arrival_date | DateTime nullable | 预计到仓 |
| status | String(20) | WAITING_APPROVAL/APPROVED/REJECTED/EXECUTED/EXPIRED |
| snapshot | JSON | 证据快照（as_of、各证据值、规则版本） |

| idempotency_key | String(255) unique | 幂等键 |

索引：sku_id、status、idempotency_key(unique)。

## 3. 状态机

### 3.1 运行状态（agent_runs.status）

```text
RECEIVED → VALIDATING → READY → CALCULATED ──┬─ DRAFTED（有草稿）
                                             └─ BLOCKED / CONSTRAINT_CONFLICT / FAILED
```

### 3.2 草稿状态（purchase_agent_drafts.status）

```text
WAITING_APPROVAL ──approve──▶ APPROVED ──write plan──▶ EXECUTED
        │
        └──────reject──▶ REJECTED
```

审批绑定：SKU + suggested_qty + snapshot + rule_version + 时间。若草稿关键内容在审批前被外部修改（本批草稿创建后不可变，故不会发生），需重新生成草稿。

## 4. 幂等设计

- 幂等键 = `{case_id or 'adhoc'}-{sku.code}-{suggested_qty}-{snapshot_id}`，其中 snapshot_id = `snap-{as_of:%Y%m%d%H%M%S}`。
- 创建草稿前先按 `sku_id + status=WAITING_APPROVAL` 查既有草稿；存在则返回既有草稿并标记 run 关联。
- `idempotency_key` 唯一约束兜底并发重复提交。
- 已 EXECUTED/APPROVED 的草稿不允许再次审批。

## 5. 证据快照（snapshot）

每次运行生成证据快照 JSON：

```json
{
  "as_of": "2026-10-09T08:00:00",
  "rule_version": "v1",
  "daily_sales": 10,
  "lead_time_days": 21,
  "safety_days": 7,
  "local_available": 20,
  "fba_available": 10,
  "in_transit_on_time": 20,
  "moq": 120,
  "case_pack": 12,
  "supply_price": "12.00",
  "supplier_name": "...",
  "quote_valid": true,
  "compliance_ok": true
}
```

快照随草稿持久化，审批时点与运行时不一致时以草稿快照为准，并回读复核。

## 6. 复用与新增决策

- **新增草稿表**而非复用 purchase_plans：草稿需保存 Agent 特有的快照/幂等/计算中间值，且不污染现有采购计划状态机；审批通过后才转换为 purchase_plans。
- 转换动作：在 approve 后由独立函数调用创建 PurchasePlan + PurchasePlanItem（status=draft），与现有 purchase_plans 提交/审批流程衔接。
