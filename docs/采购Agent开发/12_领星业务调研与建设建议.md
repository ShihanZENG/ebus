# 领星业务调研与建设建议

调研日期：2026-10-10。依据领星公开官方帮助文档，以及本项目采购 Agent、库存余额模型和数据准备功能。未登录领星客户后台；下述建设建议属于本项目的设计判断，不代表已实现或已接入领星。

## 业务主线

运营发现商品将缺货 → 计算各销售端需求 → 分配可用库存和在途 → 分别提出采购、发货建议 → 人工审批 → 采购收货、质检入库或仓库发货 → 更新库存、到货时间和成本 → 重新计算。

领星区分直发 FBA 和经海外仓中转，采购与各段发货有各自的时间范围。预计到货是否赶得上需求会影响抵扣量；销量可采用多窗口加权、固定预测或历史同期，支持异常销量处理。[来源：补货建议](https://www.lingxing.com/help/article/replenishmentAadvice)

领星全平台规划还区分海外仓补货、本地采购和订单缺货采购，采购端会汇集不同销售渠道的需求。规则可设默认值并针对商品调整。[来源：全平台补货建议](https://www.lingxing.com/help/article/allPlatformReplenishmentAdvice)

采购执行从计划、审核、采购单推进到收货、质检、入库，还要处理部分到货和变更。各阶段单据必须关联，避免计划、订单和到货重复计入供应。[来源：采购管理](https://www.lingxing.com/help/article/purchasingManagement)

库存业务需要区分良品、不良品、锁定和库存成本；库位数量与仓库库存承担不同职责。[来源：库存明细](https://www.lingxing.com/help/article/warehouseDetail)

FBA 发货计划、平台货件和实际发货单承担不同职责，后者关联实际出库及头程费用。因此创建计划后仍需跟踪执行和到仓。[来源：FBA 发货流程](https://www.lingxing.com/help/article/fbaShippingProcess)

## 本项目核查与建议

| 业务问题 | 当前可确认的实现 | 建议补充 |
| --- | --- | --- |
| 哪些商品需要处理 | SKU 选择、补货配置和数据准备检查 | 商品清单直接列出缺货风险、缺失资料、待采购及待发货状态 |
| 发多少、买多少 | 已分开输出数量，但 supply_agent.py 用含采购交期的统一 horizon 推导发货目标，再抵扣国内供应求采购量 | 分开采购覆盖期与发货覆盖期；先明确直发、中转和自发货场景 |
| 多店铺如何共用货 | 当前按配置计算，并对部分共享库存情形阻断 | 增加需求汇总与库存分配，记录每笔供应被哪个需求占用，防止重复购买或抵扣 |
| 库存能否拿来卖 | InventoryBalance 主要记录 on_hand_qty、reserved_qty | 明确待检、不良、可售、在途、库存归属与预计可用日期，统一各页面口径 |
| 新商品如何预测 | 当前供需规则使用 7/21 天销量及完整性依据 | 给新品提供有来源和有效期的人工预测；成熟商品支持可配置窗口、促销和断货处理 |
| 建议之后如何执行 | 已有草稿、审批和关联业务入口 | 补全从建议到实际收发货的跟踪，展示未执行、部分执行、延误和关闭原因 |

上述核查针对采购 Agent 的当前计算与库存基础模型，不等于整个 ERP 其他模块均无相应能力；实施前应复用已有采购、仓储和 FBA 单据。

特别说明：连续 21 天是本项目当前算法的数据要求，不能写成行业统一要求。数据库里已有 SKU 也不等于报价、销量和库存已经得到真实业务核实。

## 建议推进顺序

1. 先选一个真实 SKU 和一条实际履约路线，核实店铺、源仓、目的仓、库存归属、运输方式及实际交期；补足有效报价和销量来源。
2. 对齐库存状态及各类在途定义，再拆分采购与发货的覆盖周期。把每笔需求和供应的单据、数量、可用日期展示出来。
3. 建立多店铺需求汇总和库存分配，再开放批量生成建议。不能让不同配置独立消耗同一笔库存。
4. 打通采购到货、实际出库、签收上架的回写。重新分析时应识别已经执行的数量。
5. 在上述业务数据可靠后，再增加默认规则、批量维护、异常提醒、销量预测场景和平台同步。

Agent 的职责建议：收集已授权数据、调用确定性计算、解释缺货原因、提示缺项及生成待审单据。数量和金额应能追溯到计算与来源单据；执行状态由业务单据更新。

用户需要补充的首批资料：主要销售平台和店铺、实际履约路线、各仓库用途、一个优先上线的 SKU、该 SKU 的报价和运输箱规，以及订单和库存来自哪个系统。未知项保留待补充，不能自动填成已确认。
