## 2. 启动方法

沿用项目既有启动流程（后端 README）：

```powershell
cd backend
docker compose -p crossborder-erp up -d db        # 数据库
.\.venv\Scripts\python.exe -m alembic upgrade head  # 迁移到 0007
.\.venv\Scripts\python.exe -m app.bootstrap --demo   # 演示数据（追加，不覆盖）
.\start.ps1                                          # 启动 127.0.0.1:18080
```

前端：`cd frontend; npm run dev` → http://127.0.0.1:15173（/api 代理到 18080）。

接口文档：http://127.0.0.1:18080/docs，分组「采购 Agent」。

## 3. 演示步骤

1. 登录 → 在「采购 Agent」分组调用 `POST /api/v1/purchase-agent/decide`，请求示例：

```json
{
  "sku_id": "<演示SKU id，CUP-BLACK-500>",
  "warehouse_id": "<CN-DEMO id>",
  "as_of": "2026-09-01T08:00:00",
  "daily_sales": 10,
  "lead_time_days": 21,
  "safety_days": 7,
  "budget_limit": "3000.00",
  "case_id": "CASE-001",
  "inbound_items": [{"id": "F01", "eta": "2026-09-10T00:00:00", "qty": 20}]
}
```

2. 期望返回 status=DRAFTED，draft.suggested_qty=240、net_gap=230、target_stock=280、total_amount=2880.00。
3. 演示 SKU 需在 attributes 中配置 moq=120、case_pack=12、compliance=ok（`PATCH /api/v1/skus/{id}`）；库存通过入库单建立（本地仓 20、海外仓 10）。
4. `GET /api/v1/purchase-agent/drafts` 查看草稿 → `POST /drafts/{id}/approve` 审批 → 生成采购计划（purchase_plans）草稿。
5. 反例演示：daily_sales 传 null → BLOCKED；budget_limit 传 2000 → CONSTRAINT_CONFLICT；同一请求重复提交 → 同一草稿（幂等）。

## 4. 实际验证结果

- `pytest -q`：**64 passed**（原 54 项 + 新增 10 项），覆盖：
  - 正常样例 240（280/230/240/2880）
  - 晚到在途不计 → 252
  - null 销量 → BLOCKED
  - 预算不足 → CONSTRAINT_CONFLICT
  - 缺口为 0 → CALCULATED 无草稿
  - 幂等：重复提交同一草稿
  - 审批 → 采购计划、重复审批 409、驳回需原因
  - 权限：无 write 403、只读账号可查
  - 合规缺失 → BLOCKED
  - MOQ/箱规规则（缺口 5 → 120）
- `alembic check`：No new upgrade operations detected。
- 迁移：本地库已升级至 0007（head）。

2. **真实数据冒烟**（`backend/probe_agent_live.py`，真实 HTTP 调用）：

| 场景 | 参数 | 结果 |
|---|---|---|
| 登录 | admin（.env 凭据） | 成功 |

| A 库存充足 | 日销 5、交期 12，CN-SZ 仓（在库 1500） | CALCULATED，无草稿 |
