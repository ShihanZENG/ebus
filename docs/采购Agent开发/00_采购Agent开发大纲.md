## 2. 业务背景与目标

### 2.1 背景

- 项目已实现 SCM 采购与补货主链路：补货建议计算（`/api/v1/replenishment-suggestions/compute`）、建议调整与转采购、采购单审批、分批收货。
- AI 层尚未实现。目标架构文档规划了 AI 总助手 + 商品/运营/客服 Agent；采购 Agent 属于供应链侧受控执行 Agent，与课程"补货 Agent——从库存风险到采购草稿"一致。
- 课程核心口径：目标库存 = 日销 ×（总提前期 + 安全天数）；净缺口 = max(0, 目标库存 − 本地可售 − FBA 可售 − 按期在途)；建议量 = ceil(max(缺口, MOQ) ÷ 箱规) × 箱规；null 销量 ≠ 0；建议数量 ≠ 采购授权。

### 2.2 目标

1. 提供采购 Agent 的统一入口（decide），完成请求校验、证据校验、确定性计算、约束检查、草稿生成、审批流转。
2. 所有数字可复算、有来源、有停止条件；输出绑定快照与幂等键。
3. 只生成草稿并等待人工审批，不越权直接创建正式采购单。
4. 与现有权限体系、审计日志、采购计划/采购单流程无缝衔接。

### 2.3 一期边界（非目标）

- 不接入真实 LLM 服务（保留 L0 离线编排；L1 模型接入为可选扩展）。
- 不写入远程 ERP / 不调用平台 API。
- 不实现多 Agent 总控路由（归 AI 总助手后续阶段）。
- 不在本批实现销量预测模型（日销为输入参数或取自现有补货建议口径）。

- 供应商：报价、交期、状态

- 无 Agent 运行审计表（工具调用记录、输入输出、证据 ID）。
- 无前端 Agent 交互页。

## 4. 总体架构

```text
用户 / 采购人员（自然语言或结构化请求）
        │
        ▼
┌─────────────────────────────┐
│ 采购 Agent 编排层（本批新增）│
│ decide(request, evidence)   │
│ validate_request →          │
│ validate_evidence →         │
│ replenish()（确定性计算）    │
│ 约束检查 → compose_result   │
└──────┬──────────────────────┘
       │ 调用受控工具（只读/计算）
       ▼
┌─────────────────────────────┐
│ 工具层：复用现有后端接口      │
│ 库存 · SKU/商品 · 供应商报价  │
│ 补货建议 · 采购计划 · 审计    │
└──────┬──────────────────────┘
       ▼
数据层：ERP/WMS/SCM 数据库（PostgreSQL）
```

关键原则：

1. LLM 负责理解与解释，函数负责确定性计算。
2. 只读工具自动执行；写入（草稿/采购）一律人工审批。
3. 证据不足必须 BLOCKED，禁止把 null 当 0、禁止猜测。
4. 每次执行记录输入、输出、工具调用与快照，可审计、可复算。

## 5. 功能需求详述

### 5.1 输入与请求校验（validate_request）

- 输入字段：case_id（可选）、sku、as_of（业务时点）、market/店铺（可选）、qty 上下文（可选）。
- 校验：SKU 存在且有效；as_of 有明确值且格式正确；字段类型与必填约束（Schema）。
- 失败返回 `blocked_result(reason=...)`。

### 5.2 证据采集与校验（validate_evidence）

- 证据清单（每个证据记录来源与快照 ID）：
  1. 日销量（来源：现有补货建议口径或输入参数；明确销量窗口与 as_of）
  2. 本地可售库存（WMS/ERP 口径）
  3. FBA 可售库存（海外仓口径）
  4. 按期在途（货件 ETA 去重、过滤；到港 ≠ 可售）
  5. 总提前期（采购交期 + 物流 + 清关 + 入库，或现有字段）
  6. 安全天数
  7. MOQ、箱规
  8. 供应商报价与有效期、合规材料状态（3C 等，可选）
- 校验规则：null 销量 → BLOCKED；负库存 → BLOCKED；快照不一致 → BLOCKED；报价过期 → BLOCKED；合规缺失 → BLOCKED。

### 5.3 确定性计算（replenish）

- 目标库存 = 日销 × (总提前期 + 安全天数)
- 净缺口 = max(0, 目标库存 − 本地可售 − FBA 可售 − 按期在途)
- 若缺口 ≤ 0 → 建议量 0（不采购）
- 否则 base = max(缺口, MOQ)；建议量 = ceil(base ÷ 箱规) × 箱规
- 预算约束：货值 = 建议量 × 单价；超预算 → `CONSTRAINT_CONFLICT`（不擅自改数量）

### 5.4 停止条件与状态机

状态：`RECEIVED → VALIDATING → READY → CALCULATED → DRAFTED → WAITING_APPROVAL → APPROVED → EXECUTED`；失败 `BLOCKED / CONSTRAINT_CONFLICT / REJECTED`。

停止条件（任一如不满足即停）：缺日销、缺合规、负库存、快照不一致、在途 ETA 未知、报价过期、预算冲突、同一幂等键已执行。

### 5.5 采购草稿与审批

- 草稿内容：SKU、店铺、数量、币种、预计到仓、输入快照、计算中间值、规则版本、申请人、审批人、有效期、幂等键。
- 审批绑定：SKU + 数量 + 版本 + 快照 + 时间；关键内容变更 → 重新审批。
- 审批通过后调用写入工具（复用 purchase_plans 或新建接口）创建正式采购计划/采购单；执行后回读复核。
- 本地演示阶段只生成草稿，不调用真实采购创建（或仅在明确授权时）。

### 5.6 幂等与重复建单防御

- 幂等键生成规则：`{case_id}-{sku}-{suggested_qty}-{snapshot_id}`。
- 同一幂等键已存在草稿 → 拒绝重复创建，返回既有草稿。
- 重复提交、网络重试不产生重复采购。

### 5.7 审计与可追溯

- 记录：请求、证据快照、工具调用（名称、参数、返回）、计算中间值、结果状态、审批记录、最终动作。
- 写入审计日志（复用 `/api/v1/audit-logs` 或新增 Agent 运行表）。

## 7. API 设计（草案）

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/v1/purchase-agent/decide` | Agent 入口：输入请求 + 证据 → 返回结果（草稿/BLOCKED） |
| GET | `/api/v1/purchase-agent/runs` | 运行记录查询 |
| GET | `/api/v1/purchase-agent/runs/{id}` | 运行详情（含工具调用、中间值、快照） |
| POST | `/api/v1/purchase-agent/drafts/{id}/approve` | 审批草稿 → 转采购计划/采购单 |
| POST | `/api/v1/purchase-agent/drafts/{id}/reject` | 驳回草稿 |
| GET | `/api/v1/purchase-agent/drafts` | 草稿列表 |

## 8. 权限设计

- 新增资源名：`purchase_agent`（read/write）；`purchase_agent_drafts`（read/write/approve）或并入现有权限体系。
- 校验：写入（草稿创建、审批、转采购）必须角色权限 + 店铺/仓库范围。
- 普通角色只能读证据与结果；审批动作限采购/管理员角色。
- 审计权限沿用现有 `audit:read`。

## 12. 验收标准（草案）

1. 后端 pytest 全绿（新增用例 + 既有回归），alembic check 通过。
2. 正常样例：日销 10、交期 21、安全 7、本地 20、FBA 10、按期在途 20、MOQ 120、箱规 12 → 目标 280、缺口 230、建议 240、状态 WAITING_APPROVAL。
3. 反例：null 销量 → BLOCKED；晚到在途（20 件不可计）→ 缺口 250、建议 252；预算不足 → CONSTRAINT_CONFLICT；重复幂等键 → 不重复建单。
4. 审批通过后能按权限创建采购计划/采购单并回读复核；无权限操作被 403 拦截。
5. 每次运行可查证据快照、工具调用与中间值（可复算、可审计）。
6. 前端页面可完成"发起判断 → 查看结果 → 审批"闭环。
