## 0. 开始之前：三个地址和一个账号

| 用途 | 地址 | 说明 |
| --- | --- | --- |
| 管理后台（日常操作都在这里） | http://127.0.0.1:15173 | 图形界面，运营人员用这个 |
| 接口文档（Swagger） | http://127.0.0.1:18080/docs | 少数页面尚未做按钮的功能，需要在这里操作 |
| 接口健康检查 | http://127.0.0.1:18080/ready | 返回 `{"status":"ready","database_revision":"0004"}` 即正常 |

**登录账号**

- 用户名：`admin`（取自 `backend/.env` 的 `ERP_ADMIN_USERNAME`）
- 密码：**\<从 `backend/.env` 的 `ERP_ADMIN_PASSWORD` 获取\>**（不要把真实密码写进任何共享文档）

**新手先记住三句话**

1. 系统是"状态机"驱动的：每张单据都有状态，只能在特定状态下做特定操作，点错状态会报 `422`。
2. **库存分三档**：在库（on_hand，仓库里实际有多少件）、预留（reserved，已分配给订单但还没出库）、可售（available = 在库 − 预留）。**能不能卖，看"可售"**。
3. 系统不做汇率折算。美元单就是美元，人民币单就是人民币，各自统计。

## 1. 登录与首页看板

### 1.1 登录

1. 浏览器打开 http://127.0.0.1:15173 ，输入用户名 `admin` 和密码。
2. 登录成功后会拿到一个"令牌"，有效期 **8 小时**（由 `backend/.env` 的 `ERP_SESSION_HOURS` 控制）。超过 8 小时页面会提示重新登录。
3. **密码输错 5 次会被锁 5 分钟**，届时提示"登录暂时锁定，请稍后重试"。这时不要继续试，等 5 分钟再登，或让管理员重置密码。

### 1.2 首页看板怎么读

登录后第一屏是"业务总览"，分三块：**顶部统计卡 → 中间三个图表/待办 → 下方两张明细表**。

#### 顶部 6 张统计卡（点击卡片可直接跳到对应页面）

| 卡片 | 含义 | 数据口径 | 你该做什么 |
| --- | --- | --- | --- |
| 订单总数 | 系统里所有销售订单的条数 | 订单表总数（不分状态） | 了解规模 |
| 待审核订单 | 状态为 `draft` 的订单 | 刚建好/刚导入，还没人确认 | **去"销售 → 销售订单"点"审核"** |
| 待出库订单 | 状态为 `shipping_requested` 的订单 | 已预留库存，等仓库拣货发货 | **去"仓储 → 出库单"点"确认发货"** |
| 在手库存 | 所有仓库所有 SKU 的"在库"合计 | 含已被预留的部分 | 了解压货规模 |
| 低库存预警 | **可售库存 ≤ 120 件**的 SKU-仓库组合个数 | 阈值 120 是前端固定值 | **去"仓储 → 库存余额"看红色数字** |
| 待补货 SKU | 状态 `pending` 且建议量 > 0 的补货建议条数 | 建议量为 0 的不算待办 | **去"采购 → 补货建议"转采购单** |

> 注意：卡片统计的是"当前能看到的全部数据"，一次最多取 100 条。数据量再大时需要到对应列表页翻页。

#### 中间三块

- **销售金额（按币种）**：把订单金额按币种分组累加，**不做汇率折算**。看到 USD 和 CNY 两条并列是正常的。
- **订单状态分布**：按 待审核 / 待发货 / 待出库 / 已完成 / 售后中 / 已取消 六种状态显示占比。
- **运营待办**（可直接点击跳转）：
  - 待审核订单（`draft`）
  - 待发货订单（`approved`，已审核但还没申请发货）
  - 待确认出库单（`shipping_requested`）
  - 待审批采购单（`submitted`）
  - 待处理补货建议（`pending` 且建议量 > 0）

#### 下方两张明细表

- **库存预警**：把可售库存从低到高排序，取最少的 8 行，显示 SKU / 仓库 / 在手 / 占用（预留）/ 可用。可用 ≤ 120 的数字是红色。
- **最近订单**：最近 8 张订单的 订单号 / 客户 / 金额 / 状态 / 下单时间。

> 如果顶部出现红条"部分首页数据暂时无法加载"，说明某个模块你没有查看权限或接口临时报错，其他模块仍可正常使用，刷新即可。

## 2. 基础资料准备（必须按顺序做）

基础资料之间有依赖关系，**顺序错了会建不出来**。请严格按下表从上到下做：

| 顺序 | 菜单路径 | 做什么 | 必填项 | 关键点 |
| --- | --- | --- | --- | --- |
| ① | 基础资料 → 币种与单位 | 建计量单位、建币种 | 类型（`unit` 单位 / `currency` 币种）、编码、名称 | 系统已预置：单位 `PCS 件 / SET 套 / BOX 箱`；币种 `CNY 人民币 / USD 美元 / EUR 欧元 / GBP 英镑 / JPY 日元` |
| ② | 商品中心 → 商品 | 建"商品"（抽象款） | 商品编码、商品名称、单位 | 商品不是 SKU。一个商品下挂多个 SKU |
| ③ | 商品中心 → SKU | 建"SKU"（具体规格） | SKU 编码、SKU 名称、所属商品 | 编码要全局唯一，导入订单时靠编码匹配 |
| ④ | 基础资料 → 店铺 | 建销售店铺 | 店铺编码、店铺名称、平台渠道、站点市场、时区、**币种** | **店铺的币种决定了该店铺所有订单的币种**，选错后面建单必报错 |
| ⑤ | 基础资料 → 仓库档案 | 建仓库 | 仓库编码、仓库名称、仓库类型（国内 `domestic` / 海外 `overseas`）、国家 | 订单审核和采购收货都要指定仓库 |
| ⑥ | 基础资料 → 供应商 | 建供应商 | 供应商编码、供应商名称 | 联系人/电话/邮箱可选 |
| ⑦ | 采购 → 供货信息 | 把"供应商 ↔ SKU"配对 | 供应商、SKU；供货价（默认 0）、交期天数（默认 7） | **这一步决定补货建议转采购单时的采购单价**。没配对，转出来的单价是 0 |

### 2.1 停用 vs 删除

系统里所有基础资料都**只做"停用"，不做删除**。停用的影响：

- 停用的 SKU：不能建新订单、不能建采购单、不能入库、不能建供货信息。
- 停用的商品：它下面的所有 SKU 即使启用也不可用。
- 停用的店铺 / 仓库 / 供应商：不能被新单据引用。
- 已被单据引用过的资料**不允许删除**（会报 409），只能停用。

> 建议：资料建错了就停用，再建一条新的，**不要试图删除老数据**。

## 3. 主流程一：销售发货

### 3.1 整体链路（记住这张图）

```
待审核 draft
   │  点「审核」→ 必须选履约仓库
   ▼
待发货 approved
   │  点「申请发货」→ 系统按订单明细预留库存，生成出库单（状态 picking 拣货中）
   ▼
待出库 shipping_requested   （此时库存：在库不变、预留 +N、可售 −N）
   │  在「仓储 → 出库单」点「确认发货」→ 填运单号
   ▼
已完成 fulfilled            （此时库存：在库 −N、预留 −N）
                             订单也可在此之后进入「售后中 after_sale」
旁支：draft / approved / shipping_requested 任一状态都可点「取消」→ cancelled
      shipping_requested 取消时会自动把预留库存还回去
```

### 3.2 逐步操作

#### 步骤 1 · 创建销售订单（状态：`draft` 待审核）

- **页面**：销售 → 销售订单
- **说明**：当前前端订单页**只提供列表、审核、申请发货、取消和详情查看**，没有"新建订单"按钮。手工建单和批量导入请通过接口文档 http://127.0.0.1:18080/docs 的 `POST /api/v1/orders` / `POST /api/v1/orders/import` 完成（也可以让对接的电商平台推送）。
- **必填字段**（`POST /api/v1/orders`）：

| 字段 | 含义 | 说明 |
| --- | --- | --- |
| `shop_id` | 店铺 | 必须是启用状态的店铺 |
| `source_order_no` | 来源单号 | 平台原始订单号，**同店铺 + 同渠道下不能重复** |
| `currency_id` | 币种 | **必须与所选店铺的币种完全一致**，否则报错 |
| `items` | 订单明细 | 数组，每行：`sku_id`、`quantity`、`unit_price`、`discount_amount`（可选，默认 0） |
| `warehouse_id` | 履约仓库 | 可选，建单时可以不填，审核时再定 |
| `customer_name` / `customer_contact` / `remark` | 客户与备注 | 可选 |
| `source_channel` | 来源渠道 | 默认 `manual`（手工） |

- **金额由系统自动算**：`行金额 = 单价 × 数量 − 行优惠`；`应付金额 = 各行金额之和`。不用自己填总额。
- **常见失败原因**：
  - `422 订单币种必须与店铺币种一致` → 店铺选的是美元站，你却填了人民币。
  - `422 SKU xxx 不存在或已停用` / `SKU xxx 所属商品已停用` → SKU 编码填错或 SKU/商品被停用。
  - `422 订单明细存在重复 SKU` → 同一张订单里同一个 SKU 写了两行，请合并数量。
  - `409 同店铺同来源渠道已存在相同来源单号的订单` → 这张单已经建过了，别重复建。
  - `422 行优惠超过行金额` → 优惠金额填得比行金额还大。

**批量导入**：`POST /api/v1/orders/import` 一次可传多行，按"来源单号"自动分组（同单号多行 = 一张订单的多个商品）。导入结果返回 `created / skipped / errors` 三段：
- `created`：新建成功的单号和行号；
- `skipped`：已存在被跳过的（不会重复建）；
- `errors`：**带行号和原因**，例如"第2行：SKU 编码 NOT-EXIST-SKU 不存在"。照着行号改表格重传即可，**已成功的行不会重复创建**。

#### 步骤 2 · 审核订单（状态：`draft` → `approved`）

- **页面**：销售 → 销售订单 → 该行点「审核」
- **必填**：弹出框选择**履约仓库**（由哪个仓发货）。
- **前置条件**：订单必须是 `draft`。其他状态点审核会报 `422 只有待审核订单可以审核，当前状态 xxx`。
- ⚠️ **一个已知坑**：前端审核弹窗**默认选中仓库列表的第一条**，不是订单上指定的仓库。审核前务必确认弹窗里显示的仓库是不是正确的那一个。

#### 步骤 3 · 提交发货申请（状态：`approved` → `shipping_requested`）

- **页面**：销售 → 销售订单 → 该行点「申请发货」
- **系统做了什么**：
  1. 按订单明细逐行检查**可售库存**（在库 − 预留）是否够；
  2. 够 → 生成一张**出库单**（状态 `picking` 拣货中），把数量加到"预留"上；
  3. 不够 → **整单回滚，一行都不会预留**，报 `422 SKU xxx 可售库存不足：需要 N，可用 M`。
- **前置条件**：订单必须是 `approved`。已申请发货的订单再点一次会报 `409 该订单已有出库单，请勿重复申请`。
- **库存变化示例**（US-LA 仓 / BT-EARBUDS-BLK，原 在库 320、预留 0）：下单 2 件并申请发货后 → 在库 320、预留 2、可售 318。**注意在库没变，变的是预留。**

#### 步骤 4 · 出库确认（出库单 `picking` → `shipped`，订单 → `fulfilled`）

- **页面**：仓储 → 出库单 → 该行点「确认发货」
- **填什么**：
  - `tracking_no` 运单号（必填，建议填国际快递单号）
  - `remark` 备注（可选）
- **系统做了什么**：在库 −N、预留 −N，出库单置为 `shipped` 并记录发货时间，**订单自动变成"已完成 fulfilled"**。
- **库存变化示例**：上一步的 320 / 2 / 318 → 出库后 在库 318、预留 0、可售 318。
- **前置条件**：出库单必须是 `picking`。重复确认报 `422 出库单状态为 shipped，不能重复发货`。

#### 步骤 5 · 取消订单（旁支）

- **页面**：销售 → 销售订单 → 该行点「取消」
- **必填**：取消原因（`reason`，必填，会存进系统并进操作日志）。
- **可取消的状态**：`draft`、`approved`、`shipping_requested`。**已发货（fulfilled）、已取消、售后中的订单不能取消**。
- ⚠️ **关键**：如果订单已经进入 `shipping_requested`（已预留库存），取消时系统会**自动把预留库存还回去**，同时把对应的出库单置为"已取消"。
- **库存变化示例**：在库 318、预留 5 → 取消后 在库 318、预留 0、可售 318。

#### 步骤 6 · 登记收款（可选，不影响发货）

- 接口：`POST /api/v1/orders/{订单id}/payments`
- 必填：`amount` 金额、`currency_id` 币种（**必须与订单币种一致**）；可选：`method` 方式、`source` 来源、`paid_at` 收款时间、`remark` 备注。
- 已取消的订单不能登记收款。

### 3.3 销售发货 · 快速排错表

| 现象 | 原因 | 怎么办 |
| --- | --- | --- |
| 点"审核"没反应 / 报错 | 订单不是"待审核" | 刷新列表看状态 |
| 申请发货报"可售库存不足" | 该仓库这个 SKU 的可售数量不够 | 先去"仓储 → 库存余额"确认；做入库单或采购收货补货；或改从别的仓库发货 |
| 申请发货报"该订单已有出库单" | 已经申请过了 | 去"仓储 → 出库单"找对应出库单确认发货 |
| 出库单列表里找不到 | 该出库单所属仓库不在你的仓库权限范围 | 找管理员放开仓库范围 |
| 取消时报错 | 订单已完成/已取消/售后中 | 已完成订单请走售后流程，不能取消 |

## 4. 主流程二：采购补货

### 4.1 整体链路

```
补货建议计算（pending 待处理）
   │  人工确认/修改建议量 → 点「转采购单」
   ▼
采购单 草稿 draft
   │  点「提交审批」
   ▼
采购单 待审批 submitted       （首页"待审批采购单"计数的是这一档）
   │  点「审批」通过 → approved ；点「驳回」→ rejected
   ▼
采购单 已审批 approved
   │  分批收货（可多次，每次填收货单号）
   │  · 合格数量 → 直接进仓库在库库存
   │  · 不合格数量 → 只记录，不进可售库存
   │  · 收齐 → 系统自动置为 closed 已完成
   ▼
采购单 已完成 closed
旁支：submitted 可「驳回 rejected」；除 closed / cancelled 外可「取消 cancelled」；
      approved 且全部收齐时可「关闭」；未收齐强行关闭会报 422。
```

> ⚠️ **采购单只有这几种状态**：`draft`（草稿）→ `submitted`（待审批）→ `approved`（已审批）→ `closed`（已完成），外加 `rejected`（已驳回）、`cancelled`（已取消）。
> **不存在"部分收货 / 已收货"状态**——部分收货时采购单**仍然显示"已审批"**，要看收了多少，请打开采购单详情看明细的"已收 / 订购"。

### 4.2 逐步操作

#### 步骤 1 · 计算补货建议

- **页面**：采购 → 补货建议 → 点「计算补货建议」
- **填什么**（弹窗）：

| 字段 | 含义 | 默认值 |
| --- | --- | --- |
| SKU | 要算哪个 SKU | 必选 |
| 仓库 | 补到哪个仓 | 必选 |
| 供应商（可选） | 建议向谁采购 | 不填则后面不能转采购单 |
| 日均销量 | 平均每天卖多少件 | 1 |
| 交期（天） | 下单到到货要多少天 | 7 |
| 安全库存 | 额外多备多少件 | 0 |

- **补货公式怎么读**（系统按此计算，结果可追溯）：

```
再订货点 reorder_point = round(日均销量 × 交期天数) + 安全库存
有效库存 effective_stock   = 该仓库该 SKU 的可售库存（在库 − 预留）
有效在途 effective_in_transit = 该仓库该 SKU 在"已审批"采购单上还没收到的数量
建议量 suggested_qty = max(0, 再订货点 − 有效库存 − 有效在途)
```

- **实例**（本次实操真实数据，US-LA 仓 / 便携蓝牙音箱黑色）：

| 输入/中间值 | 数值 |
| --- | --- |
| 日均销量 | 20 |
| 交期天数 | 12 |
| 安全库存 | 80 |
| 有效库存 | 260 |
| 有效在途 | 0 |
| 再订货点 | round(20 × 12) + 80 = **320** |
| 建议量 | 320 − 260 − 0 = **60** |

- 建议量为 **0** 表示"暂时不用补"（库存 + 在途已经盖住再订货点），此时**不能转采购单**。
- **重复计算**：对同一个"SKU + 仓库"再算一次，会**覆盖**原来那条待处理建议的数量和参数，不会新增第二条。

#### 步骤 2 · 人工调整建议量（可选但推荐）

- **页面**：采购 → 补货建议 → 该行"调整"（接口 `PATCH /api/v1/replenishment-suggestions/{id}`）
- **填什么**：`suggested_qty` 新的建议量（必填）、`reason` 调整理由（建议填，会留存）。
- **什么时候需要改**：系统算的是纯公式值，遇到促销、大促备货、供应商起订量（MOQ）、整箱发货等情况，需要人工上调。
- **限制**：已经转成采购单（`turned_into_po`）的建议不能再改。
- **本次实操**：把 60 改为 100，理由"按促销计划上调至 100"，保存成功后建议量变 100、状态仍为 `pending`。

#### 步骤 3 · 转采购单（建议 → 草稿采购单）

- **页面**：采购 → 补货建议 → 该行点「转采购单」
- **系统做了什么**：
  1. 生成一张**草稿采购单**，采购单号自动生成（格式 `PO-YYYYMMDD-XXXX`，如 `PO-20261008-812E`）；
  2. 明细只有一行：SKU = 建议的 SKU，数量 = 建议量，单价 = **供货信息里该供应商对该 SKU 的供货价**（没维护供货信息则单价为 0）；
  3. 建议状态变为"已转采购单"。
- **前置条件（缺一不可）**：建议量 > 0、建议上填了供应商、SKU 和供应商都是启用状态。
- **重复点会怎样**：报 `409 该建议已转为采购单，请勿重复提交`，**不会生成两张单**。
- ⚠️ **已知显示问题**：转单成功后，补货建议列表的"状态"列会显示英文 `turned_into_po` 而不是中文"已转采购单"。这是前端文案没覆盖到该状态，不影响数据，看到英文即表示已转单成功。

#### 步骤 4 · 提交审批（草稿 → 待审批）

- **页面**：采购 → 采购单 → 该行点「提交审批」
- **前置条件**：只有 `draft` 能提交。重复提交报 `422 只有草稿可以提交审核，当前状态 xxx`。
- 提交后首页"待审批采购单"计数 +1。

#### 步骤 5 · 审批（待审批 → 已审批）

- **页面**：采购 → 采购单 → 该行点「审批」
- **前置条件**：只有 `submitted` 能审批。
- **驳回**：采购单行点「驳回」，填写 1～480 字原因后确认；接口 `POST /api/v1/purchase-orders/{id}/reject` 请求体为 `{"reason":"..."}`。只有 `submitted` 能驳回；原因保存在采购单备注和操作审计中。驳回后变 `rejected`，**不能再审批**（如需再买请重新建单）。
- ⚠️ **改单会掉状态**：已审批的采购单如果修改了**明细内容**（数量/单价），系统会把它**退回 `submitted` 待审批**，需要重新审批一次。只改"预计到货日期"或"备注"不会掉状态。

#### 步骤 6 · 分批收货（核心！一次可以只收一部分）

- **页面**：⚠️ 前端**暂未提供收货按钮**，请在 http://127.0.0.1:18080/docs 用 `POST /api/v1/purchase-orders/{采购单id}/receipts` 操作。
- **前置条件**：采购单必须是 `approved`。草稿、待审批、已关闭都不能收货。
- **请求体**：

| 字段 | 含义 | 必填 |
| --- | --- | --- |
| `receipt_no` | 收货单号 | **必填，全局唯一**，建议用"PO号-批次1" |
| `received_at` | 收货时间 | 可选，默认当前时间 |
| `remark` | 备注 | 可选 |
| `items[].po_item_id` | 采购明细行 id | **必填**（在采购单详情里取，不是 SKU id） |
| `items[].quantity_accepted` | 合格数量 | 必填，> 0 时**直接进仓库在库库存** |
| `items[].quantity_rejected` | 不合格数量 | 可选，默认 0；**只记录，不入库、不算可售** |

- **分批收货怎么操作**：同一张采购单**做多次收货**，每次换一个新的 `receipt_no`。
- **本次实操**：订购 100 件
  - 第 1 次：`MANUAL-VERIFY-RCV-001`，合格 40 → 库存 260 → 300，采购单**仍是"已审批"**，明细显示 已收 40 / 订购 100；
  - 第 2 次：`MANUAL-VERIFY-RCV-002`，合格 60 → 库存 300 → 360，**系统自动把采购单置为"已完成 closed"**。
- **收货的坑**：
  - `receipt_no` 重复 → `409 相同收货单号已存在`，**不会重复累加库存**，请换一个单号重交。
  - 收货单号建议提前编号登记，避免重复。
  - **历史问题已修复**：早期实操曾发现超量收货未被拦截；当前接口先校验累计合格与不合格数量，超出订购数量会返回 422，且不会写入库存。见本节当前注意事项。

#### 步骤 7 · 关闭采购单

- **自动**：所有明细"已收 ≥ 订购"时，系统在收货那一刻**自动关闭**，不用手动点。
- **手动**：接口 `POST /api/v1/purchase-orders/{id}/close`，要求状态为 `approved` **且**所有明细已收齐。有未收齐的明细会报 `422 存在未收齐的明细，无法关闭`。
- **取消**：接口 `POST /api/v1/purchase-orders/{id}/cancel`，必填 `reason` 取消原因；`closed` 和 `cancelled` 不能再取消。

### 4.3 采购补货 · 快速排错表

| 现象 | 原因 | 怎么办 |
| --- | --- | --- |
| 转采购单报"建议未指定供应商" | 计算建议时没选供应商 | 重新计算一次并选上供应商，或手工建采购单 |
| 转采购单报"建议数量为 0" | 库存+在途已够，公式算出 0 | 不用补；确需补就先人工把建议量改成正数 |
| 转出的采购单单价是 0 | 该"供应商 ↔ SKU"没维护供货信息 | 去"采购 → 供货信息"补一条，再重转（或手工改单） |
| 收货报"只有已审核采购单可以收货" | 单子还是草稿/待审批/已关闭 | 先走完提交 + 审批 |
| 收货报"相同收货单号已存在" | 单号用重了 | 换新单号 |
| 收货报"收货明细不属于该采购单" | `po_item_id` 填错（填成了别张单的明细 id） | 打开该采购单详情，复制它自己明细行的 id |
| 采购单显示"已审批"但明明收了一部分 | 正常，部分收货不改变状态 | 看明细的"已收 / 订购"列 |

## 5. 售后处理

售后分两类：**退货 `return`** 和 **退款 `refund`**。

### 5.1 发起售后

- **页面**：销售 → 售后（也可用接口 `POST /api/v1/orders/{订单id}/after-sales`）
- **前置条件**：订单状态必须是 `approved`（待发货）、`shipping_requested`（待出库）或 `fulfilled`（已完成）。**待审核和已取消的订单不能发起售后。**
- **填什么**：

| 字段 | 含义 | 必填 |
| --- | --- | --- |
| `type` | 类型：`return` 退货 / `refund` 退款 | 是 |
| `reason` | 原因说明 | 是 |
| `quantity` | 数量（退货件数） | 否，默认 0 |
| `amount` | 退款金额 | 否，默认 0 |
| `remark` | 备注 | 否 |

- 提交后：生成一条售后记录（状态 `pending` 待处理），**订单状态立刻变成"售后中 `after_sale`"**。

### 5.2 处理售后

- **页面**：销售 → 售后 → 该行点「已处理」
- **接口**：`POST /api/v1/after-sales/{售后id}/resolve`，必填 `status`，只能填 `completed`（同意）或 `rejected`（拒绝）。
- ⚠️ **两条重要提醒**：
  1. 售后处理完成后，**订单状态仍然是 `after_sale`，不会自动回到"已完成"**。要恢复请找管理员在数据库/后台处理。
  2. **退货不会自动把库存还回仓库**。系统只记录售后数量和金额，实物回仓请自己在"仓储 → 库存余额/入库单"做入库或盘点调整。
- 同一条售后记录不能重复处理，重复点会报 `422 售后记录已是 completed 状态，不能重复处理`。

## 6. 库存查询、调整与流水追溯

### 6.1 库存余额怎么看

- **页面**：仓储 → 库存余额
- 可按仓库、按 SKU 筛选。三列数字含义：

| 列名 | 含义 | 能不能卖 |
| --- | --- | --- |
| 在库 `on_hand_qty` | 仓库里实际有多少件 | — |
| 预留 / 占用 `reserved_qty` | 已被订单申请发货占住、还没出库的数量 | 不能 |
| 可售 `available_qty` | **在库 − 预留** | **能卖的就是这个** |

- 首页"低库存预警"看的就是**可售 ≤ 120**。

### 6.2 手工入库（增加在库）

- **页面**：仓储 → 库存余额 → 点「手工入库」
- **填什么**：仓库（必选）、SKU、数量（必填）；供应商可选。
- **生效时机**：**保存即在库 +N，不需要二次确认**，同时生成一条 `inbound` 流水。
- 入库单状态直接是 `confirmed`。

### 6.3 盘点调整（把在库改成某个数）

- **页面**：⚠️ 前端**暂未提供按钮**，请用 http://127.0.0.1:18080/docs 的 `POST /api/v1/warehouses/{仓库id}/inventory/adjust`。
- **填什么**：`sku_id`、`on_hand_qty`（**调整后的最终数量**，不是增减量）、`reason`（调整原因，必填）。
- **系统做了什么**：算出差额 = 最终数量 − 当前在库，改在库数量，并写一条 `adjust` 流水，备注就是你的原因。**不动预留数量。**
- **实例**：当前在库 5，填 12 → 生成一条 `on_hand_delta = +7` 的 adjust 流水，备注"盘点调整为 12"。
- 每次盘点都会进操作日志，责任可追溯，**请如实填写原因**。

### 6.4 库存流水追溯

- **页面**：仓储 → 库存流水
- 可按仓库、SKU、**流水类型**筛选，按时间倒序（最新在前）。

**流水类型对照表**

| 类型 `txn_type` | 什么时候产生 | 在库变动 | 预留变动 |
| --- | --- | --- | --- |
| `inbound` | 手工入库 **或** 采购收货合格品入库 | +N | 0 |
| `reserve` | 销售订单申请发货（预留） | 0 | +N |
| `release` | 取消已预留的订单（释放） | 0 | −N |
| `outbound` | 出库单确认发货 | −N | −N |
| `adjust` | 盘点调整 | ±差额 | 0 |

**怎么用它查问题**

- 某个 SKU 数量对不上 → 按"仓库 + SKU"筛出全部流水，从最早一条往后加总，就能还原每一笔变动。
- 采购收货的流水类型是 `inbound`，备注形如"采购收货 MANUAL-VERIFY-RCV-001"，可以直接反查收货单号。
- 出库流水的备注形如"出库发货 tracking=XXX"，可以直接反查运单号。
- 流水**只能追加、不能修改或删除**，是所有库存争议的判定依据。

### 6.5 操作日志

- **页面**：系统 → 操作日志
- 记录所有 create / update / approve / submit / cancel / receipt / adjust / resolve 等动作，含操作人、对象、动作、变更前后快照。
- 出现数量或状态争议时，**先查库存流水看数字怎么变的，再查操作日志看是谁点的**。

## 7. 权限与账号

### 7.1 三种控制维度

系统用三层来控制"谁能看什么、做什么"：

1. **角色**：决定能进哪些页面、能点哪些按钮。
2. **功能权限**：细到"读 / 写"，例如 `orders:read`（看订单）、`orders:write`（审核、发货、取消）。
3. **行级范围**：决定能看到**哪些店铺的数据**、**哪些仓库的数据**。

### 7.2 角色怎么配

- **页面**：系统 → 账号与角色（**只有 admin 能进**）
- 系统预置两个角色：

| 角色编码 | 角色名称 | 权限范围 |
| --- | --- | --- |
| `admin` | 系统管理员 | 全部权限，不受功能权限清单限制 |
| `viewer` | 基础资料只读 | 只能看商品、SKU、店铺、供应商、仓库、币种单位，**看不到订单/库存/采购** |

- **新建角色**：填角色编码（`code`）、角色名称（`name`）、勾选权限清单（`permissions`）。
- **修改角色权限**：角色卡片点「编辑权限」，改完保存后立即生效（已登录用户下次请求即生效）。
- **权限命名规则**：`<模块>:<read|write>`。完整清单（共 32 项）：

```
after_sales   字典   audit          dictionaries   inbound_orders
inventory     orders payment_records  products     purchase_orders
purchase_receipts  replenishment  shipments      shops        skus
supplier_skus suppliers         warehouses
```
每项都有 `:read` 和 `:write` 两种（audit 只有 `audit:read`）。

> 经验：**看数给 `:read`，干活给 `:write`**。例如客服只处理售后，就给 `orders:read` + `after_sales:read` + `after_sales:write`。

### 7.3 行级范围怎么理解

- **`shop_scope` 店铺范围**：控制销售侧数据——订单列表、订单详情、售后记录。**留空 = 看全部店铺**；填了店铺列表 = 只能看到这些店铺的订单。
- **`warehouse_scope` 仓库范围**：控制仓储侧数据——库存余额、库存流水、入库单、出库单、仓库档案。**留空 = 看全部仓库**。
- ⚠️ **两条容易踩的坑**：
  1. 两个范围是**独立的两把锁**，互不相通。给了店铺范围不代表能看库存，还要单独给仓库范围。
  2. 超出范围的记录**不是提示"无权限"，而是直接查不到**（列表里根本不出现，按 id 查会返回 404"不存在"）。如果运营说"这张单我明明建过却找不到"，先查他的店铺范围。

### 7.4 新建账号

- **页面**：系统 → 账号与角色 → 「新建账号」
- **必填**：用户名、初始密码、角色；可选：是否启用、店铺范围、仓库范围。
- **重置密码**：账号行点「重置密码」。⚠️ **重置密码会把该账号所有已登录的会话全部踢下线**，对方需要重新登录。
- **停用账号**：把"是否启用"关掉即可，不要删除账号（历史单据和日志都引用了账号）。

## 8. 常见问题与报错含义

### 8.1 HTTP 状态码速查

| 提示 | 含义 | 典型场景 | 怎么处理 |
| --- | --- | --- | --- |
| **422** | 校验失败 / 状态不对 | 必填字段没填、金额格式错、币种不匹配、单据状态不允许当前操作、库存不足 | **看 message，系统会把原因写得很具体**（如"SKU BT-EARBUDS-BLK 可售库存不足：需要 99999，可用 318"） |
| **409** | 冲突（重复） | 来源单号重复、收货单号重复、补货建议重复转单、该订单已有出库单、被引用的资料不能删除 | 说明"已经做过了"，**不要重复提交**；确认是重复就去列表里找已有的那条继续操作 |
| **403** | 没有权限 | 提示"没有此功能的操作权限"、"只能在授权店铺下创建订单"、"仅管理员可管理账号和角色" | 找管理员加权限/加店铺范围 |
| **401** | 未登录或会话过期 | 提示"请登录"、"会话无效或已过期" | 重新登录（会话默认 8 小时） |
| **429** | 登录暂时锁定 | 提示"登录暂时锁定，请稍后重试" | 连错 5 次锁 5 分钟，等一会儿再试 |
| **404** | 找不到 / 不在可见范围 | 单据 id 填错，或该单据所属店铺/仓库不在你的权限范围 | 核对 id；确认权限范围 |
| **200 / 201** | 成功 | 201 表示新建成功 | — |

### 8.2 高频报错逐条解释

| 报错原文 | 白话 | 怎么办 |
| --- | --- | --- |
| `订单币种必须与店铺币种一致` | 店铺是美国站（USD），你建单选了人民币 | 改币种，或换到对应币种的店铺 |
| `店铺不存在或已停用` | 店铺被停用了或 id 填错 | 到"基础资料 → 店铺"启用 |
| `SKU xxx 不存在或已停用` / `SKU xxx 所属商品已停用` | SKU 停用，或者它所属的商品被停用了 | 逐级检查商品和 SKU 的启用状态 |
| `订单明细存在重复 SKU` | 一张单里同一 SKU 写了两行 | 合并成一行，数量相加 |
| `行优惠超过行金额` | 优惠金额 > 单价 × 数量 | 调小优惠 |
| `同店铺同来源渠道已存在相同来源单号的订单` | 这张单建过了 | 去列表用来源单号搜 |
| `只有待审核订单可以审核，当前状态 xxx` | 已经审核过了（或已发货/售后中） | 刷新看状态 |
| `只有已审核订单可以申请发货，当前状态 xxx` | 还没审核，或已申请过 | 先审核；已申请则去出库单确认 |
| `SKU xxx 可售库存不足：需要 N，可用 M` | 可售库存（在库 − 预留）不够发这一单 | 补货（入库/采购收货）或换仓库 |
| `该订单已有出库单，请勿重复申请` | 已申请过发货 | 去"仓储 → 出库单"确认 |
| `出库单状态为 shipped，不能重复发货` | 这张出库单已发过 | 不用再点 |
| `只有未发货订单可以取消，当前状态 xxx` | 已发货/售后中的订单不能取消 | 走售后流程 |
| `该建议已转为采购单，请勿重复提交` | 重复点"转采购单" | 去采购单列表找已生成的那张 |
| `建议数量为 0，无需采购` | 库存和在途已够 | 不用补；确需补先改建议量 |
| `建议未指定供应商，无法转采购单` | 计算建议时没选供应商 | 重算一次选上供应商 |
| `只有草稿可以提交审核，当前状态 xxx` | 已经提交过了 | 刷新看状态 |
| `只有已提交的采购单可以审核，当前状态 xxx` | 还是草稿，或已驳回 | 驳回的单要重新建 |
| `只有已审核采购单可以收货，当前状态 xxx` | 没审批，或已关闭 | 走完审批；已关闭的不能再收 |
| `相同收货单号已存在` | 收货单号重复 | 换一个唯一单号 |
| `收货明细不属于该采购单` | `po_item_id` 填错 | 从该采购单详情里取明细 id |
| `存在未收齐的明细，无法关闭` | 还有货没到 | 继续收货，或取消该单 |
| `只有已审核或已申请发货的订单可以发起售后，当前状态 xxx` | 订单还是待审核 | 先审核 |
| `售后记录已是 completed 状态，不能重复处理` | 已经处理过了 | 不用再点 |
| `请求字段无效 / Field required` | 必填字段没传 | 对照第 3、4 章的字段表补齐 |

### 8.3 非报错类疑问

| 问题 | 答案 |
| --- | --- |
| 销售金额为什么不换算成人民币？ | 系统当前不做汇率折算，按订单原币分别统计。需要统一口径请导出后自行折算。 |
| 采购单收货一部分后状态怎么没变？ | 正常。采购单在部分收货时**仍是"已审批"**，全部收齐才自动变"已完成"。看明细的"已收 / 订购"。 |
| 订单已发货，还能取消吗？ | 不能。请走售后流程。 |
| 售后处理完，订单怎么还是"售后中"？ | 系统设计如此，售后处理不改变订单状态、不自动回补库存。实物回仓请手工入库或盘点调整。 |
| 想删掉建错的商品/SKU？ | 删不掉（被引用会报 409）。请停用，再建一条正确的。 |
| 页面上有功能找不到按钮？ | 目前**采购收货、盘点调整、采购单驳回/关闭/取消、订单新建与批量导入**这几项前端没有按钮，请用 http://127.0.0.1:18080/docs 操作。 |
| 数据看起来不对怎么办？ | 先查"仓储 → 库存流水"还原数字变化，再查"系统 → 操作日志"定位操作人和时间。 |

### 10.5 实测发现的、与预期不符或需要注意的地方

1. **超量收货已由后端拦截**：收货接口会把本次合格与不合格数量合并校验，超过采购明细剩余数量时返回 422；校验整张回执通过后才写入库存。请仍核对实收数量和质量分类。
2. **部分收货没有独立状态**：采购单不存在"部分收货/已收货"状态，收货未齐时状态仍是 `approved`，需打开详情看明细的"已收/订购"。
3. **售后处理不回滚订单状态、不回补库存**：售后处理完成后订单仍为 `after_sale`，退货实物需另行入库或盘点。
4. **已审批采购单改明细会退回待审批**：修改数量/单价后状态由 `approved` 掉回 `submitted`，需要重新审批。
5. **前端订单页审核默认取仓库列表第一条**，不是订单自带仓库，审核时务必确认。
6. **主要操作已有前端入口**：采购收货和采购单驳回/关闭/取消位于采购单页面；库存盘点调整位于库存页面；订单新建和批量导入分别位于订单页面及“导入订单”页面。若账号看不到按钮，请核对对应读写权限。
7. **补货建议状态文案**：转采购单后的状态值为 `turned_into_po`，页面应显示为“已转采购单”；若当前构建仍显示英文，请刷新前端并报告页面位置。
8. **订单状态用语**：`shipping_requested` 表示订单已申请履约、等待仓库处理。订单列表与首页当前均显示“待出库”。
9. **重置密码会踢掉该账号全部登录会话**；连续 5 次登录失败会锁 5 分钟。
