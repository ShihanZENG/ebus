# 27 退款记录

> **实现状态：未实现（退款流水/退款执行）**。OMS 有售后申请记录，但没有财务退款流水或实际退款接口。

## 业务说明

本主题规划记录退款申请、退款执行结果及资金流水，供财务核对。当前 OMS 的 `AfterSale` 是订单售后业务记录：可创建退款/退货类型的申请，保存申请金额、原因、数量和状态；处理状态为待处理、完成或驳回。把售后标记为完成不表示系统已经向客户退款，也不会生成退款流水、支付渠道退款凭证或实际退款时间。

DataLab 的 `dws_finance_day` 汇总可能包含类型为“退款”的外部汇总行，但当前页面只是通用财务汇总展示，OMS 没有将该行作为本地退款单或与售后申请关联。

## 操作路径

- 订单售后申请：订单详情/售后管理中的售后流程。
- 本文所述财务退款记录页面：当前未实现。

## 规划字段

退款单号、原订单、关联售后申请、申请金额、实际退款金额、币种、原因、退款时间、支付渠道、渠道流水号、执行状态及备注。

## 数据来源与接口

- 本地售后表：`after_sales`，保存申请，不是退款流水。
- DataLab 页面数据：`GET /api/v1/datalab/table/dws_finance_day`，属于外部日汇总，不能作为本地退款明细。
- 当前没有退款流水表或 OMS 实际执行退款的接口。

## 目标流程与建议实现边界

建议按“申请—审核—执行—渠道确认—核销”拆分业务状态。客服/运营先创建售后申请；具备退款审核权限的人员审核金额、币种和可退余额；财务人员发起退款或登记线下退款；系统保存渠道请求/响应及渠道流水号；只有渠道明确成功或经授权人员确认线下完成后，退款流水才进入成功状态。失败和超时应可重试/人工核实，重试必须使用幂等键，避免重复退款。售后申请完成状态不得自动代表退款成功。

建议新增 `RefundRecord`（退款流水）对象，至少包含退款单号、订单 ID、售后 ID、订单币种 ID、申请金额、实际退款金额、原因、状态、退款渠道、渠道流水号、申请/执行/完成时间、操作者、失败码/失败说明、幂等键及备注；保存每次渠道交互的审计信息，限制敏感支付凭证访问。金额需校验为正数且币种与原订单一致；退款累计额不能超过已收且尚未退款的金额。部分退款、多次退款、取消退款以及渠道超时的判定规则需在开发前确定。

建议页面入口为“财务 → 退款记录”（新建路由及菜单权限），提供退款列表/详情、按日期/订单/售后/状态/渠道筛选、审核与执行动作、失败重试和导出。建议接口为退款列表/详情、创建或关联退款申请、审核、执行/重试及渠道回调接口；这些都是规划名称，当前不可调用。权限建议拆分退款读取、审核和执行，店铺范围必须跟随原订单校验，并对执行和重试动作留审计。

## 建议验收

1. 创建与订单关联的部分退款，审核并执行成功后，退款流水保存原订单币种、实际金额、渠道流水号及时间，订单与售后详情可追溯同一退款 ID。
2. 同一幂等键重复执行不得产生第二笔实际退款；金额大于可退余额、币种不一致、订单不在授权店铺范围内时拒绝并返回明确错误。
3. 模拟渠道失败及超时：失败不得标记成功；超时应进入待核实状态，安全重试不能重复退款。线下退款应要求有权限的操作者填写凭证/备注并留下审计记录。
4. 退款列表按筛选条件准确返回记录并分页；DataLab 日汇总不得被当作退款逐笔流水。
