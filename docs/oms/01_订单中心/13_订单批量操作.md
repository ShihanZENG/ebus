# 13 订单批量操作

## 文档状态

当前订单页面无复选框、行选择状态、批量操作栏或批量订单 API。

## 当前能力

页面可逐条审核、申请发货或取消。后端 `POST /api/v1/orders/import` 是批量创建导入接口，接受 JSON 行数据并按来源单号分组；它不执行批量审核、取消或导出。

## 状态与规划

- **已实现**：单笔订单操作；CSV/TSV 上传或粘贴预览后，由页面转换为 JSON 行数据批量导入。
- **未实现**：批量选择、批量审核、批量取消、Excel 导出、批量打印、批量修改物流渠道或备注。
- **规划中**：实现批量动作前需规定逐单失败处理、权限校验、库存副作用及审计记录。

## 代码位置

- 页面：`frontend/src/pages/Orders.tsx`
- 导入接口及单笔订单操作：`backend/app/orders.py`
- 导入 schema：`backend/app/schemas.py` 的 `OrderImport`、`OrderImportRow`

## 批量操作目标流程（规划，当前不可操作）

**当前已具备的批量能力是订单创建导入。**“销售 → 订单导入”页面可解析 CSV/TSV 并预览，再将 1–1000 行 JSON 数据交给后端；后端按来源单号分组，同单号行组成一笔订单，已存在订单组返回 `skipped`，无效 SKU、重复 SKU 或行优惠超过行金额使该组返回错误，其他组仍可成功。结果分别包含 `created`、`skipped`、`errors` 和计数，行号从首条数据行起算，不含表头。导入成功订单为 `draft`，不会审核或预留库存。订单列表没有复选框或批量操作栏。

### 建议批量动作设计

建议先实现批量取消和批量审核，再评估批量申请发货；每个动作都应接收明确订单 ID 列表、操作原因/仓库等参数，返回逐单成功或失败，不采用“整批失败且不知哪条失败”的响应。设置单次数量上限，执行前检查重复 ID、店铺范围、当前状态及所需字段；每笔订单单独审计，但整笔订单的副作用保持原子性。批量发货必须明确“每单独立成功，失败单回滚”，不得对一笔订单的多个 SKU 部分预留。

建议新增 `POST /api/v1/orders/batch-cancel`、`POST /api/v1/orders/batch-approve` 等接口（仅建议路径），权限为 `orders:write`，并遵守每单 `shop_scope`；审核须确认仓库权限和有效性。页面加行选择、跨页选择规则、选择数量/状态提示和二次确认，批量失败导出/复制结果。导出则需另外定义字段白名单、敏感客户信息访问权限及最大行数。

### 建议验收

混合选择 `draft`、`fulfilled` 和范围外订单执行批量取消，预期逐单成功/拒绝且不越权；批量审核缺仓时整条订单失败并可识别原因；批量申请发货时一笔缺货订单不应部分预留，也不应阻止其他合法订单按已定义的逐单策略执行；重复请求需幂等或明确告知已处理。验证大批量超上限被拒，审计记录包含操作者及每笔结果。以上接口、页面和验收均为规划，当前未实现。
