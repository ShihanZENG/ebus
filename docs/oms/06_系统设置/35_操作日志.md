# 35 操作日志

> **实现状态：部分实现**。后端记录多类写操作及登录/退出行为，管理页面支持按资源筛选、分页和查看变更快照；页面没有提供按操作人筛选或导出。

## 业务说明

审计日志记录操作者、时间、资源类型、记录 ID、动作及可用的变更前后快照。日志内容取决于业务操作是否调用审计记录逻辑；不应将其描述为对系统中每次读取或所有行为的完整记录。日志查询要求具备审计权限和全店铺、全仓库范围。

## 日志内容

- 操作人 ID、操作时间
- 资源/模块、记录 ID、动作类型
- 可选的变更前与变更后 JSON 快照
- 登录及退出事件（动作记录为 login/logout）

## 操作路径

系统设置 → 操作日志。

## 数据来源与接口

- 本地表：`audit_logs`。
- 接口：`GET /api/v1/audit-logs`，支持 `actor_id`、`resource`、`record_id`、`date_from`、`date_to` 和分页参数。
- 页面当前开放资源筛选、分页、刷新及快照查看。

## 查询细节与访问限制

`GET /api/v1/audit-logs` 支持 `actor_id`、`resource`、`record_id`、`date_from`、`date_to`、`page`、`page_size`；默认每页 20、最大 100，按创建时间倒序。`date_to` 是开区间。接口需要 `audit:read`，且调用者必须同时拥有全店铺和全仓库范围；任一范围为受限列表都会返回 403。这是全局审计查询，不提供按用户自身范围裁切的日志视图。

页面路由 `/audit-logs` 只提供资源下拉筛选、分页、刷新和前后 JSON 快照查看。虽然后端接受操作人、记录 ID 和时间范围，页面没有这些筛选控件；资源下拉选项也只列出常见资源，空选项才查询所有资源。记录 ID 以截断形式显示，但可复制完整 ID。页面将快照 JSON 展示在弹层中，较大快照可滚动查看。

审计对象字段为 `actor_id`、`resource`、`record_id`、`action`、`before`、`after`、`created_at`。当前日志是按代码中显式调用 `record_audit` 写入，未覆盖所有读取行为，也不能据此承诺每个写操作都有日志；例如具体接口需逐个核对是否调用。页面没有导出、保留期限或篡改检测机制，日志不应被描述为不可篡改的合规审计仓。

## 建议验收

1. 使用具备 `audit:read` 且两类范围均为全范围的账号查询，默认分页返回最新日志；`page_size=101` 应被参数校验拒绝，指定日期结束时间边界的记录不包含在 `date_to` 当刻之后的结果中。
2. 缺少 `audit:read` 返回 403；店铺或仓库任一为有限范围即返回 403；过期/撤销会话返回 401。
3. 对一个已接入审计的新增/修改操作，确认操作者、资源、记录 ID、动作和前后快照符合变更；登录、退出事件可按 `auth` 资源查询。不得把未接入审计的写接口推定为已记录。
4. 页面资源筛选及翻页结果与 API 一致，前后快照可读。操作人、记录 ID、时间范围筛选和导出只有在新增前端功能后才列为验收项。
