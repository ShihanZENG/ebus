# Storefront → 独立 OMS 订单镜像

ERP 的 `SalesOrder` 是权威订单。Storefront 结账与 ERP `OmsOutboxEvent` 在同一个数据库事务中提交。独立 Worker 把事件送到 OMS；OMS 只保存创建时镜像，不生成另一张可履约订单。事件只包含订单、店铺、仓库、币种、SKU 的 ID、数量和金额，不含顾客联系方式或地址。

## 启动

先启动 ERP 和 OMS 的数据库，并确认 ERP 迁移已执行。OMS 启动时自动创建镜像表。为两个进程设置**相同**的 `OMS_BRIDGE_SECRET`，由部署者生成并保存在本机环境变量或密钥管理器中，不提交到 Git。

在 OMS 后端目录启动服务（`OMS_DATABASE_URL` 必须指向独立 OMS 库）：

```powershell
$env:OMS_DATABASE_URL = '<独立 OMS 数据库连接串>'
$env:OMS_BRIDGE_SECRET = '<同一随机密钥>'
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 18090
```

在另一个终端的 ERP `backend` 目录启动 Worker；它从 `backend/.env` 读取 `DATABASE_URL`：

```powershell
$env:OMS_BRIDGE_URL = 'http://127.0.0.1:18090'
$env:OMS_BRIDGE_SECRET = '<同一随机密钥>'
.\.venv\Scripts\python.exe -m app.oms_outbox_delivery --loop
```

`--once` 只处理一个待送事件，可用于手工检查。持续处理必须使用 `--loop` 并由进程管理器守护。跨机器连接需用 HTTPS；Worker 拒绝非本机的明文 HTTP。

## 对账与故障排查

ERP 的 `oms_outbox_events` 表保留 `order_id`、`idempotency_key`、`status`、`attempt_count`、`next_attempt_at`、`last_error` 和 `delivered_at`。成功后 `status=delivered`；OMS 不可用或确认内容不匹配时回到 `pending` 并按间隔重试。运行 OMS 后，具有 `orders:read` 权限且没有店铺/仓库范围限制的员工可通过 `GET /api/v1/erp-order-mirrors/{ERP订单ID}` 查询镜像及原始 `source_order_no`。ERP 与 OMS 的店铺、仓库 ID 尚无映射，受限员工暂不能查询镜像。镜像不在 OMS 独立 `/api/v1/orders` 的履约列表中。

排查前先在 ERP 库只读查询最近未送达事件：

```sql
SELECT id, order_id, status, attempt_count, next_attempt_at, last_error
FROM oms_outbox_events
WHERE status <> 'delivered'
ORDER BY created_at DESC
LIMIT 50;
```

`processing` 超过两分钟的事件会被运行中的 Worker 重新领取。持续 `409` 表示同一订单键在 OMS 已有不同快照，应按 `order_id` 核对两端，修正数据来源后再处理，不直接删除或覆盖镜像。轮换密钥时暂停 Worker，更新 OMS 与 Worker 的 `OMS_BRIDGE_SECRET`，重启两者；暂停期间事件留在 ERP 待送队列。

同一事件重发返回同一镜像；相同 ERP 订单 ID 或事件键但内容不同返回 `409`，应核对两端数据，不能覆盖镜像。该版本只交接创建时快照；后续订单状态以 ERP 为准。
