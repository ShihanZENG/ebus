# 18 售后原因统计

## 实现状态

**尚未实现统计能力。** 售后记录只存自由文本 `reason`；客服工单只有 `subject/description`。系统没有标准原因字典、统计 API、报表页面或导出。原因文本不能直接等同可比较的分类数据。

## 业务场景与目标口径（规划）

运营需要发现退货/退款主要原因，比较店铺、SKU 和时间趋势，改进商品描述、包装或履约。统计需区分售后申请、批准金额、实际退款和实际收货数量，不能把申请值称为已退款或已退货。

建议先定义：

- 统计周期和业务时区；按申请创建时间还是完成时间筛选。
- 原因分类字典（如质量、尺寸不符、错发、物流、客户取消）和可选备注；保留旧文本并支持迁移映射。
- 申请数、涉及订单数、订单行数分别统计；同订单多笔售后不能误算成多个订单。
- 售后率分母为同店铺/时间窗内有效订单数，并明确取消订单和重复售后的处理方式。
- 申请金额、批准金额与渠道确认的实际退款额分开；按币种分组，不能直接相加不同币种。

## 当前入口与数据

- `/after-sales` 是售后明细列表，不是统计页；没有原因筛选或图表。
- `after_sales.reason` 是申请文本；`type` 为 refund/return；`quantity/amount` 是登记值。`customer_tickets.subject/description` 是工单内容，不应并入售后原因报表。
- 当前没有售后统计接口；只能查单笔订单的售后子资源，没有全局售后查询端点。

## 需新增的数据、接口与页面（建议）

- 新增原因分类/子分类字典及售后记录分类 ID，保留自由文本说明和分类变更审计。
- 新增受权限与店铺范围控制的汇总/明细查询，支持时间、店铺、类型、原因、SKU、币种筛选；响应给出统计口径、更新时间和分页明细。大结果集由服务端汇总。
- 新增售后分析页，展示趋势、原因分布、店铺/SKU 排名并可下钻；导出沿用同一筛选和权限。

## 建议验收（未执行）

1. 两条记录选不同原因后按店铺/日期筛选，汇总与明细去重口径一致。
2. 一个订单有退款与退货两条记录时，申请数为 2、涉及订单数为 1。
3. 两币种金额分别展示，不显示未经折算的混合总额。
4. 无权店铺不进入结果；分页/导出总数一致；客服工单不混入售后统计。
5. 空结果、无效日期和大结果集有明确反馈，报表显示口径及更新时间。
