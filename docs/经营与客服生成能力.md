# 经营与客服生成能力

## 启用

运行 `backend/.venv/Scripts/python.exe -m alembic upgrade head`，启动后端与前端，登录后打开 **工具 → 经营与客服生成**。使用现有 `PURCHASE_AGENT_LLM_BASE_URL`、`PURCHASE_AGENT_LLM_API_KEY`、`PURCHASE_AGENT_LLM_MODEL` 模型配置；未配置或模型连接失败时接口返回错误。API 也可在 `/docs` 调用。

所有生成接口要求登录，并执行店铺范围校验。利润与费用复算需要 `finance_agent:write`，广告需要 `advertising_agent:write`，客服生成需要 `customer_tickets:read`，工单升级需要 `customer_tickets:write`，规则维护仅管理员可用。生成结果存入 `agent_generations`，规则存入 `agent_knowledge_rules`，每次写入均有操作审计。

模型调用会把计算结果或工单内容及适用规则发送到 `.env` 配置的模型服务。接入真实客户消息和财务数据前，应确认所用模型服务符合企业的数据处理要求。

## 统一人工审核

每条生成记录初始为 `review_status=pending`。`GET /api/v1/generation-reviews` 可按生成类型、审核状态和分页查询；结果同时受用户店铺范围与业务读权限限制。利润及费用复算使用 `finance_agent:read`，广告使用 `advertising_agent:read`，客服使用 `customer_tickets:read`。

仅管理员可调用 `POST /api/v1/generation-reviews/{generation_id}/decision`，传入 `approved` 或 `rejected`；驳回必须填写原因。审核后保存审核人、时间和备注并写入审计日志。一条记录只能审核一次，重复审核返回冲突；审核通过只表示生成结果已经人工核准，不自动执行申诉、改预算、退款或发送回复。

## 利润与对账

`POST /api/v1/agent-generations/profit`。提供 `shop_id`、`source_reference`、期间、三位币种、`lines`。每行需有唯一的 `source_event_id`、`category`、正金额 `amount`；可选 `settlement_deducted` 表示该费用确实已从平台结算扣除。类别为 `sale/refund/cogs/platform_fee/advertising/logistics/tax/settlement_other`。可提供 `reported_settlement` 对照。

服务端计算净销售、贡献、已知费用后结果、应结额和差额；模型仅根据这些结果写解释草稿。销售、采购成本与平台费必须各有来源行，已核实为零时可显式填 `0.00`，缺项不能当零。相同来源行号会被拒绝，金额均按输入币种计算，不做未经证实的汇率转换。不同口径的结果不会合并成“最终净利润”。真实业务需要按账单、采购凭证和广告报表逐行登记，且为费用行正确标识是否已从结算扣除。

`POST /api/v1/profit-reconciliations/fee-discrepancies` 对单笔平台费用做证据复算。只有账单行、费用代码、交易类型与日期、适用费率及生效期、计费基数、实扣额和调整记录完整时，才可能给出 `CONFIRMED_OVERCHARGE`；缺证据、费率不适用或存在待入账调整时保持人工复核。相同证据哈希不会重复保存。

## 广告与经营

`POST /api/v1/agent-generations/ads`。提供 `shop_id`、`source_reference`、期间、币种和 `rows`。每行包括唯一 `source_row_id`、`campaign_id`、`attribution_window_days`（7 或 14）、曝光、点击、花费、归因订单和归因销售。

按活动及窗口分别合计，再计算 CTR、CPC、CVR、ACOS、ROAS。零分母指标返回 `null`；零销售行的花费仍进入总体花费，避免低估 ACOS。归因指标只描述报表口径，不能单凭相关性证明增量销售。

## 客服与合规

管理员调用 `POST /api/v1/agent-generations/rules` 录入规则，字段包括 `rule_code`、`version`、`status`、`market`、`category`、`effective_from`、可选 `effective_until`、`source_reference` 和 `content`。`PATCH /api/v1/agent-generations/rules/{id}/status` 可发布或撤回。录入者必须核对规则来源和授权发布状态。

`POST /api/v1/agent-generations/customer/{ticket_id}` 传 `category` 和 `as_of`。系统读取用户可见的真实工单，只选择已发布、市场/类目/日期匹配的规则；无规则或同一规则有多个同时适用的发布版本时阻断。模型返回 JSON 草稿和规则 ID，服务端校验引用及部分高风险承诺。发热、冒烟、鼓包等安全信号要求草稿明确升级。输出总是 `may_send=false`，需要人工核对、决定和发送。提示注入测试仍需在接入真实规则后持续验证。

人工确认需要升级后，调用 `POST /api/v1/customer-tickets/{ticket_id}/escalate`，提供升级原因、目标处理人和备注。系统只允许启用且拥有对应店铺范围的管理员、客服主管或合规专员承接；安全与合规风险提升为 `urgent`，其他升级为 `high`，并写入工单事件和审计日志。当前升级仍无 SLA 到期、签收和通知机制。

## 当前边界

- 平台结算、广告平台和汇率源尚未自动同步；数据由有权限的人员从真实报表提交。`source_reference` 是追溯入口，不能单独证明数据真实。
- 客服规则库起初为空，必须由管理员从已批准材料录入。没有规则时不会生成客服草稿。
- 模型文字是待审核解释，服务端确定性计算结果才是金额和指标的依据；生成不修改采购量、广告预算、退款或工单状态。
- 当前页面接受结构化 JSON 明细，尚无 CSV 导入和逐行字段映射向导。
