# 渠道对接：多平台自动拉单

## 1. 为什么必须有这一块

在此之前，系统里订单的 `source_channel`（来源渠道）和 `source_order_no`（来源单号）**只是两个字段，
不是「真的从平台拉过」的证据**。所有订单要么手动建，要么批量导入。
换句话说，这套系统此前是**内部进销存**，不是跨境电商 ERP。

区别在哪：真 ERP 的订单是**平台推过来或定时拉回来的**，系统负责接住、去重、审单、履约、回写。
少了这一层，后面所有的自动审单、防超卖、轨迹回传都没有落点。

这个模块补的就是「接住」这一步。

## 2. 四张表各自负责什么

| 表 | 作用 | 关键约束 |
|---|---|---|
| `channel_connections` | 一家店铺在某个平台上的连接配置（同步模式、状态、非敏感设置） | 唯一 `(shop_id, channel_code)` |
| `channel_sync_jobs` | 一次拉单的账本：拉到几笔、新建几笔、跳过几笔、失败几笔 | 计数非负检查 |
| `channel_sku_mappings` | 平台商品编码 → 本地 SKU 的对照表 | 唯一 `(connection_id, external_sku)` |
| `channel_order_records` | 平台订单在本地的镜像，保存原始载荷 | 唯一 `(connection_id, source_order_no)` |

**为什么要在订单之外再存一份镜像？** 因为订单表只记「我们怎么理解这笔单」，
镜像表记「平台当初给了什么」。对账、排查、状态回写都要用原始信息，
而订单会被人工编辑、合并、改价，不能当作平台数据的可信副本。

## 3. 三条硬规则

### 规则一：平台来的单，出生即 draft

不管平台说这笔单已付款还是已发货，进到系统一律是 `draft`（草稿），
不许直接变成 `approved` 去占库存。

原因和上一节讲的一样：推过来的单可能是重复的、缺货的、地址错的、疑似欺诈的。
一进来就锁库存，等发现问题时仓库已经白干了。**审核这道闸门对所有来源一视同仁。**

代码上这一点是复用了 `orders.py` 里现成的 `validate_order_refs` 和 `build_items`，
保证平台单和手动单走完全相同的校验口径，不会出现「平台单绕过校验」的口子。

### 规则二：幂等，同一笔单重复推送不生成两张

幂等键是 `(connection_id, source_order_no)`。平台网络重试、你手动点了两次同步、
webhook 和定时拉取撞车——这些情况都会重复收到同一笔单。

处理方式是**跳过而不是报错**：刷新镜像里的平台状态和同步时间，不新建订单。
返回值里 `skipped_count` 会记账。

### 规则三：密钥不落库

`credential_ref` 只保存**环境变量的键名**，真实密钥运行时从环境变量读。
数据库被拖走也拿不到平台凭据。

webhook 签名密钥读 `ERP_CHANNEL_WEBHOOK_SECRET`；**这个变量没配置时 webhook 入口直接停用**（返回 503），
而不是「跳过校验照单全收」——安全默认值必须是关。

## 4. 单笔失败不影响整批

拉单时逐笔用数据库 savepoint 隔离。某笔单的 SKU 没映射、币种对不上，
只把这笔记进 `error_count` 并写明原因，同批其他单照常入库。
最后任务状态：`success`（全成）/ `partial`（部分成）/ `failed`（全败）。

## 5. 端点清单

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/channels/connections` | 连接列表 |
| POST | `/api/v1/channels/connections` | 新建连接 |
| GET | `/api/v1/channels/connections/{id}` | 连接详情（含映射条数） |
| PATCH | `/api/v1/channels/connections/{id}` | 改同步模式/状态/设置 |
| POST | `/api/v1/channels/connections/{id}/test` | 配置自检（**不访问外网**） |
| GET | `/api/v1/channels/connections/{id}/sku-mappings` | SKU 映射列表 |
| POST | `/api/v1/channels/connections/{id}/sku-mappings` | 新增 SKU 映射 |
| POST | `/api/v1/channels/connections/{id}/sync` | 主动拉一次单 |
| GET | `/api/v1/channels/sync-jobs` | 同步日志 |
| GET | `/api/v1/channels/orders` | 平台订单镜像 |
| POST | `/api/v1/channels/orders/{id}/push-shipment` | 跟踪号回写 |
| POST | `/api/v1/channels/webhook/{channel_code}/{shop_code}` | 接收平台推送（靠签名，无需登录） |

权限：`channels:read` / `channels:write`。

## 6. 怎么亲手跑一遍

用演示适配器（`mock` 渠道），全程不访问外网：

```bash
# 1. 建连接：拉 2 笔演示单，商品用本地已有的 CUP-BLACK-500
curl -X POST /api/v1/channels/connections -H "Authorization: Bearer $TOKEN" -d '{
  "shop_id": "<店铺ID>", "channel_code": "mock", "sync_mode": "polling",
  "settings": {"mock_sku": "CUP-BLACK-500", "mock_count": 2}
}'

# 2. 拉单
curl -X POST /api/v1/channels/connections/<连接ID>/sync -H "Authorization: Bearer $TOKEN" -d '{}'
# -> fetched_count=2, created_count=2

# 3. 再拉一次
# -> fetched_count=2, created_count=0, skipped_count=2   （幂等生效）

# 4. 去看订单，状态应为 draft
curl "/api/v1/orders?shop_id=<店铺ID>" -H "Authorization: Bearer $TOKEN"
```

想模拟「又来了一批新单」，把连接的 settings 改成带 `mock_stamp` 的值即可
（默认单号是稳定的，这样才能验证幂等）。

## 7. 刻意没做、也没假装做了的部分

诚实列出来，避免误判能力边界：

- **只有 `mock` 适配器能主动拉单和回写。** Amazon / Shopee / TikTok 等渠道调用会明确返回
  「未内置实现」错误，而不是返回空列表假装没单。接真实平台需要各自的适配器实现。
- **没有真正的定时调度器。** `/sync` 是手动触发；要真轮询需外加调度任务（APScheduler / cron）。
- **没有平台库存、价格、Listing 的反向同步。** 目前只做「订单从平台进来」和「跟踪号回平台」两个方向。
- **webhook 只做了签名校验和时间窗防重放**，没有做平台各自的回执确认协议。
