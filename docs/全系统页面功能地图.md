# 全系统页面功能地图

> 目的：承接「页面功能 + UI 设计」任务的第一层——先建立**全系统页面清单与职能地图**，作为后续逐页详细设计的索引。
> 范围：主系统前端 `frontend/src/pages/`、独立 OMS 前端 `oms/frontend/src/pages/`、Storefront 单页应用。
> 数据来源标注（你的硬约定「演示数据必须标来源」）：
> - **真实**：页面读取/写入后端业务库（ERP / OMS 各自库）。
> - **演示**：明确 `not_charged`、不扣款、不作真实履约（仅 Storefront 结账与查单）。
> - **治理**：LIM 控制台，接真实接口但部分能力为 demo 边界（只读、Sandbox、证据分类）。
> 说明：职能描述基于文件名、README 模块说明与既有审计报告归纳；逐页详细 UI 设计前请以实际组件为准复核。

## 四、规模与下一步

- **主系统前端**：约 60 个页面文件；**独立 OMS**：19 页；**Storefront**：1 个 SPA。合计约 80 个页面入口。
- **重复风险**：OMS 与主系统在 orders / customers / tickets / core-inventory 等同源双实现（P0 工程债，待决策合并或写边界）。
- **演示边界**：仅 Storefront 结账/查单为 demo（not_charged）；其余为真实业务数据；LIM 为治理层（真实接口 + demo 边界）。
- **详细 UI 设计**：按 `docs/LIM页面功能与UI设计.md` 的模板，逐批产出「功能定位 + 信息架构 + 核心交互 + 数据真实性标注 + 改进建议」。建议优先级：
  1. 订单 `Orders.tsx`（核心履约链路 + 审计发现的超卖边界）
  2. 库存 `Inventory.tsx` / `InventoryAllocation.tsx`
  3. 采购 `Purchase.tsx` / `PurchasePlansPage.tsx`
  4. 售后 `AfterSalesPage.tsx` / 客服 `CustomerTicketsPage.tsx`
  5. 财务 `FinanceSettlementsPage.tsx` / 广告 `AdCampaignsPage.tsx`
  6. 独立 OMS 19 页（合并决策后再统一设计）
