# 跨境电商系统：一期完成目标与验收标准

> 状态：目标草案，供下一批开发前对齐。当前代码仓库有本地 ERP/OMS/WMS/SCM 与 AI 原型；本文中的真实平台接入和试点验收均是目标，不表示已完成。

## 一句话完成目标

把当前以本地数据和演示流程为主的系统，推进为一个**面向跨境卖家小团队、接入一个真实销售渠道、能可靠完成一条核心运营闭环**的可试用 MVP：业务数据可追溯，流程状态可核对，AI 只提供有来源的草稿/解释，关键业务写入由有权限的人确认。

这是一项目标假设，不代表目标用户和产品市场需求已经验证。第一期不以“Agent 数量”或“菜单页面数量”作为完成标准。

## 完成范围

### 0. 开发前的决策门

开始真实渠道接入前，必须明确：

1. **首发渠道**：建议优先考虑 Amazon（当前商品/Listing 方向和系统场景已有基础），但只有在开发者具备合法授权账号、API 权限和测试数据时才选它；否则选实际可接入的渠道。
2. **履约模式**：FBA、FBM 或两者。履约路径不同，不能用同一套“发货闭环”验收。
3. **首批使用角色**：先按“店铺负责人/运营”这一工作假设设计，试点时确认是否合适。
4. **数据授权与环境**：明确使用官方 API、沙箱或经授权的卖家账号；不得把模拟数据报告成真实同步结果。

如果渠道 API、账号授权或必要权限暂时拿不到，应先完成 CSV/报表导入的可审计数据试点，不伪造实时连接。

### 1. 一条真实数据链

- 至少接入一个渠道的一家试点店铺；第一版采用只读同步，不自动改平台数据。
- 同步范围先限定为支撑所选闭环所需的数据：商品/SKU 与 Listing 映射、订单、库存或履约状态、相关结算数据。逐字段确认源接口和权限，不承诺渠道没有提供的字段。
- 保存外部 ID、来源渠道、店铺、原始/规范化状态、币种、业务时间、抓取时间、最近同步游标/批次及失败原因。
- 支持重复拉取、增量同步、有限重试与人工重试；更新不能制造重复单，失败不能静默丢失。
- SKU/Listing 匹配不确定时进入待处理队列，不由 AI 自行绑定。

### 2. 一条可操作的订单履约闭环

- 公共步骤：渠道订单进入本地系统 → 去重与 SKU 映射 → 展示明确状态/异常 → 授权人员处理 → 操作与结果可审计。
- **FBM**：订单审核 → 库存预留 → 仓库出库 → 录入/同步物流单号 → 回读可获得的平台状态。任何库存不足、缺少地址或同步失败都必须有明确结果，不能显示成功。
- **FBA**：同步订单和 Amazon 履约状态、库存及可获得的货件/结算信息；不把平台仓库履约伪装成本地 WMS 出库。
- 取消、部分履约、重复通知、退款/退货、API 超时等异常有明确状态和人工处理入口。第一期可限定异常种类，但不得丢弃未知状态。

### 3. 一条可核对的结算链

- 可以导入/同步与试点闭环对应的结算明细，并保留来源、币种、期间和原始记录 ID。
- 定义销售、退款、平台费用、广告、物流、税费、采购成本的口径；未知费用显示为未计/待核对，不默认填零。
- 结算金额与渠道报告不一致时产生可定位的差异项，记录差异金额、原因状态、处理人和处理时间；未解决差异不得显示为“已对平”。
- SKU 利润指标明确包含和不包含哪些费用，不能把部分贡献利润称为净利润。

### 4. AI 能力的边界与验收

- Listing 助手可读取真实同步的商品事实，生成多语言草稿、缺失资料、关键词字面覆盖和修改说明；每项事实应能回看来源资料，无法确认的内容标记待核实。
- 其他 Agent 只能访问当前用户和店铺有权限的数据；回答标明数据来源/时间范围。涉及外部写入或高风险业务动作时，先生成草稿，由授权人员确认。
- 不接入实时平台规则库时，必须明示“未做实时规则校验”；关键词出现不等于 SEO 排名保证。
- 建立固定评测集，覆盖正常、缺资料、冲突、过期、越权和诱导模型编造等案例。测试通过不等于模型永远不会犯错；保留人工复核与审计。

## 一期验收标准

| 类别 | 可验收标准 |
|---|---|
| 真实来源 | 每条试点记录可追溯到渠道/导入文件、店铺、外部 ID、业务时间与同步批次；真实与模拟数据能明确区分 |
| 完整性 | 用双方确认的试点样本逐条对照源端；核心 ID、数量、金额、币种和状态字段无静默漏记/重复。差异全部可见并可分类 |
| 幂等与恢复 | 对同一时间段/文件重复同步至少两次，不产生重复业务记录；模拟超时/断网后可重试并可查看失败原因 |
| 履约正确性 | 按选定 FBA/FBM 模式跑通约定的正常路径；不足库存、取消、未知状态和平台超时均不会被误报为成功 |
| 对账可信 | 试点结算样本按已定义口径核对；所有差异都进入待核对状态，未处理差异不被隐藏或计入“已对平” |
| 权限与审计 | 店铺范围外和无权限账号无法读取/写入；生成、审核、同步、人工改绑、重试与业务动作均留下操作者和结果 |
| AI 质量 | 固定测试集中，输出的商品事实均可映射到输入资料或明确标为待核实；越权数据不出现在回答里；拒绝无依据认证/功效承诺 |
| 可运维 | 管理者能查看最近成功/失败同步、错误原因和重试结果；部署、备份恢复和故障处理文档与当前版本一致 |
| 试点使用 | 至少一名真实运营人员用授权数据完成约定任务，并记录实际耗时、人工修正、失败点和是否回到原表格流程；无真实试用时只能称“技术 MVP”，不能称“已验证产品” |

样本规模和准确率阈值须在选定渠道、可用测试环境及字段契约之后再定。当前不硬填一个百分比，以免在数据范围未确定时制造虚假精度；但“无静默漏单/重复、差异可见、越权被拦截”是硬性底线。

## 明确不属于一期完成目标

- 一次接入 Amazon、Shopify、TikTok Shop、Shopee 全部渠道。
- 自动竞价、自动改价、自动发布 Listing、自动退款或无人值守采购。
- 覆盖所有国家/税制/物流承运商，或宣称实时全量库存与绝对准确利润。
- 先搭建通用长期记忆/RAG 平台，再寻找业务问题。
- 为了“多 Agent”而给每个菜单配一个 Agent。

这些方向必须由试点痛点、接口可行性和收益证据单独立项。

## 建议开发顺序

1. **定门槛**：选首发渠道、履约模式、试点店铺/账号条件、必要字段和授权方式。
2. **做数据链**：只读连接/导入、外部 ID 映射、同步批次、幂等、错误队列。
3. **完成闭环**：围绕选定 FBA/FBM 路径，打通订单、库存/履约及异常处理。
4. **补结算核对**：导入真实结算样本、定义费用口径、展示差异。
5. **接 AI**：把 Listing 草稿接到真实商品资料，用证据展示和人工审核验收。
6. **试点复盘**：按表中指标测任务完成情况，再决定扩渠道或扩 Agent。

## 当前项目对照

- 已有本地 ERP/OMS/WMS/SCM 主流程、店铺/用户权限、审计、Listing 草稿审核和部分 AI 原型。
- 渠道拉单文档明确真实 Amazon/Shopee/TikTok 等适配器尚未完成；模拟渠道不等于真实连接。
- 广告、财务、统计目前主要是有限的只读数据页面；平台结算导入/差异对账仍需完成。
- 采购与补货已有较完整的本地业务闭环；应复用，但不因此把供应链 Agent 当成真实平台库存同步。
- 备份恢复与运维已有基础，应在每次新增正式数据集成后重新演练。

## 首个开发批次的待确认输入

- 首发渠道：建议 Amazon（条件是能合法获得 API 授权与测试数据）；否则填实际可用渠道。
- 履约模式：FBA / FBM / 先选其一。
- 试点数据入口：官方 API / 官方报表导入 / 其他经授权来源。
- 可用于验收的脱敏样本：商品/Listing、订单、库存或履约、结算记录。
- 真实运营试用联系人：若暂无，先做技术验收，并明确商业需求未验证。
