# 跨境电商 ERP —— 数据库备份与恢复说明

> 适用范围：`backend` 服务使用的 PostgreSQL 15（容器 `crossborder-erp-db-1`，镜像 `postgres:15-alpine`，宿主 `127.0.0.1:15432` → 容器 `5432`）。
> 文档中所有密码均以 `***` 占位，真实凭据只存在于 `backend/.env`（不纳入版本库）。

---

## 1. 组件

| 文件 | 作用 |
| --- | --- |
| `backend/scripts/backup_db.py` | 用容器内的 `pg_dump` 导出备份（默认 custom 格式 `-Fc`），输出到 `backend/backups/` |
| `backend/scripts/restore_db.py` | 用容器内的 `pg_restore` 把备份恢复到**指定目标库** |
| `backend/backups/` | 备份文件存放目录，命名 `erp_YYYYMMDD_HHMMSS.dump` |

两个脚本都通过 `docker exec` 调用容器内的 `pg_dump` / `pg_restore`，**宿主机不需要安装 PostgreSQL 客户端**；连接信息从 `backend/.env` 读取（`DATABASE_URL`，缺失时回退 `POSTGRES_USER/PASSWORD/DB`），密码通过 `-e PGPASSWORD=...` 传给容器，不在代码或命令行历史中硬编码。

运行环境统一使用项目虚拟环境：

```bash
cd backend
./.venv/Scripts/python.exe scripts/backup_db.py
```

## 2. 备份

### 2.1 基本用法

```bash
# 默认：输出到 backend/backups/erp_YYYYMMDD_HHMMSS.dump
./.venv/Scripts/python.exe scripts/backup_db.py

# 指定输出目录
./.venv/Scripts/python.exe scripts/backup_db.py --out-dir D:/erp-backups

# 只保留最近 10 份，删除更旧的（默认不清理）
./.venv/Scripts/python.exe scripts/backup_db.py --keep 10
```

### 2.2 参数

| 参数 | 默认值 | 说明 |
| --- | --- | --- |
| `--out-dir` | `backend/backups` | 备份输出目录，不存在时自动创建 |
| `--env-file` | `backend/.env` | 读取连接信息的环境文件 |
| `--container` | `crossborder-erp-db-1` | 数据库容器名 |
| `--format` | `custom` | `custom`(`-Fc`) / `plain`(`-Fp`) / `tar`(`-Ft`)；**推荐 custom**，可配合 `pg_restore` 做单表恢复与并行恢复 |
| `--keep N` | 不清理 | 保留最近 N 份，删除更旧的；删除前校验数量，超过 50 个文件直接中止（safe-delete 守卫） |
| `--quiet` | 关闭 | 减少输出 |

### 2.3 输出内容

脚本执行后会打印：实际执行的 `docker exec` 命令（密码打码）、备份文件绝对路径、**文件大小（字节 / KiB）**、**SHA-256 校验值**，并用 `pg_restore -l` 读取备份目录表（TOC）验证文件结构完整、可被恢复。

### 2.4 作为模块调用

```python
from pathlib import Path
from scripts.backup_db import run_backup

path = run_backup(out_dir=Path("backups"), keep=10)
```

## 3. 恢复

### 3.1 安全护栏（重要）

1. `--target-db` **必填**。不填直接报错退出，拒绝在目标不明的情况下恢复。
2. 目标库名与源库（`.env` 中的库名）相同时**默认拒绝**，必须显式追加 `--force`：

   ```
   [restore] 失败: 目标库 'erp' 与源库同名，恢复会覆盖现有数据。
   如确需覆盖，请显式追加 --force（建议先备份当前库）。
   ```
3. 恢复前先检查目标库是否存在；不存在则报错并给出 `createdb` 提示，或加 `--create-db` 自动建库。
4. `--clean` 默认关闭。开启后 `pg_restore` 会带 `--clean --if-exists`，**会先 DROP 目标库中的同名对象**，仅在确认目标库可覆盖时使用。
5. `--dry-run` 只打印将要执行的命令，不做任何写操作，可用于上线前预演。

### 3.2 基本用法

```bash
# 1) 先建目标库（推荐显式建库，便于确认）
docker exec -e PGPASSWORD=*** crossborder-erp-db-1 createdb -U erp erp_restore_test

# 2) 预演：只看命令
./.venv/Scripts/python.exe scripts/restore_db.py \
    backups/erp_20261008_201520.dump --target-db erp_restore_test --dry-run

# 3) 真正恢复，并打印恢复后的关键表行数
./.venv/Scripts/python.exe scripts/restore_db.py \
    backups/erp_20261008_201520.dump --target-db erp_restore_test --verify
```

省略 `backup_file` 时，脚本自动取 `backend/backups/` 下**最新**的一份备份。

### 3.3 参数

| 参数 | 默认值 | 说明 |
| --- | --- | --- |
| `backup_file` | 最新一份 | 备份文件路径（位置参数，可省略） |
| `--target-db` | **必填** | 目标库名 |
| `--container` | `crossborder-erp-db-1` | 数据库容器名 |
| `--create-db` | 关闭 | 目标库不存在时自动 `createdb` |
| `--clean` | 关闭 | 追加 `--clean --if-exists`（危险，会 DROP 同名对象） |
| `--jobs N` | 1 | 并行恢复工作数 |
| `--dry-run` | 关闭 | 只打印命令，不执行 |
| `--force` | 关闭 | 允许恢复到与源库同名的库 |
| `--verify` | 关闭 | 恢复后打印关键表行数 |

### 3.4 完整灾难恢复流程（覆盖生产库）

```bash
# 0) 先备份当前状态，留一条退路
./.venv/Scripts/python.exe scripts/backup_db.py

# 1) 停止后端服务，避免恢复过程中仍有连接写入
# 2) 恢复到源库（必须显式 --force，按需加 --clean）
./.venv/Scripts/python.exe scripts/restore_db.py \
    backups/erp_YYYYMMDD_HHMMSS.dump --target-db erp --force --clean --verify

# 3) 校验数据、重启后端服务
```

### 4.4 两张差异表的定位与结论

`audit_logs`（555 vs 554）和 `auth_sessions`（31 vs 30）各差 1 行。逐行比对源库多出的记录：

```
auth_sessions 多出 1 行: token_hash=f394e882…, expires_at=2026-10-08 20:15:59.160428
audit_logs    多出 1 行: id=34990eab-68e2-4f28-900b-562277f938cd, created_at=2026-10-08 12:15:59.161206 (UTC)
```

两行的产生时间均为 **20:15:59（本地时间）**，而备份快照开始于 **20:15:20**。即：这两行是在 `pg_dump` 取完快照**之后**才由仍在运行的后端服务写入源库的。恢复库的时间戳上界正好停在快照时刻（`audit_logs` 最大 `created_at` = 12:15:00 UTC）。

**结论：差异来自「备份后源库持续写入」的正常漂移，不是恢复失败或数据丢失。** 如需零漂移的备份，应在备份期间停止写入，或改用 PITR/WAL 归档方案。

## 5. 注意事项与风险提示

1. **不要在源库 `erp` 上直接做恢复演练**。恢复请始终先落到 `erp_restore_test` 之类的临时库，核对行数与关键数据后再决定是否切库。
2. **恢复到生产库 = 覆盖现有数据**。脚本已强制要求 `--target-db`，且目标库与源库同名时必须再加 `--force`；执行前请务必先按第 2 节做一次全量备份。
3. **`--clean` 会 DROP 目标库中的同名对象**，不可撤销；仅在确认目标库可被覆盖时使用，且建议配合 `--dry-run` 先确认命令。
4. **备份期间源库仍在写入**：`pg_dump` 在单个事务内取一致性快照，备份本身是自洽的，但恢复后的库会缺少备份时刻之后产生的增量（本次演练中 `audit_logs` / `auth_sessions` 就是这种情况）。对一致性要求极高的场景，应在备份窗口内停止后端写入，或启用 WAL 归档做时间点恢复（PITR）。
5. **custom 格式（`-Fc`）是默认且推荐的选择**：压缩体积小（本次 142 KiB），支持 `pg_restore` 按表选择性恢复、并行恢复；`plain` 格式是纯 SQL 文本，只能用 `psql` 整体回放。
6. **备份文件包含全部业务数据**（用户、会话、审计日志等敏感信息）。`backend/backups/` 应纳入 `.gitignore`，并限制目录访问权限；异地保存时注意加密与传输安全。
7. **恢复后记得核对 `alembic_version`**。若备份与当前代码 migration 版本不一致，恢复后需补跑 `alembic upgrade head`。
8. **定期验证可恢复性**。无法恢复的备份等于没有备份，建议按第 4 节的流程定期做一次「建临时库 → 恢复 → 比行数 → 删临时库」的演练。
9. **密码来源**：脚本只从 `backend/.env` 读取，请勿把 `.env` 提交到版本库，也不要把真实密码写进文档、脚本或命令行示例。
10. **`--keep` 清理有上限保护**：单次待删除文件超过 50 个时脚本直接中止，避免误删整目录；清理动作是逐个 `os.remove`，不会递归删除目录。

## 6. Storefront 本地演示文件备份

`backend/scripts/backup_db.py` 只备份 PostgreSQL，不包含 `storefront-media` 商品图片和 `storefront-support` 客服附件。可用 `backend/scripts/storefront_file_backup.py` 单独制作及校验两类文件的 ZIP 快照；清单记录规范化相对路径、字节数和 SHA-256，不记录顾客信息字段。

```bash
# 停止商城订单、客服附件和媒体写入后，在 backend 目录操作
python scripts/backup_db.py
python scripts/storefront_file_backup.py backup --output backups/storefront_files_YYYYMMDD_HHMMSS.zip
python scripts/storefront_file_backup.py verify backups/storefront_files_YYYYMMDD_HHMMSS.zip

# 恢复先只做完整性和目标冲突预演
python scripts/storefront_file_backup.py restore backups/storefront_files_YYYYMMDD_HHMMSS.zip
# 只有核对预演结果并准备好空目标目录后，才明确执行恢复
python scripts/storefront_file_backup.py restore backups/storefront_files_YYYYMMDD_HHMMSS.zip --apply
```

- 文件备份只处理媒体和客服附件；数据库仍需按本说明先恢复到隔离目标库。它不会恢复数据库、迁移或环境变量。
- 恢复会先验证清单、ZIP 路径、文件大小和 SHA-256；目标文件已存在时整体拒绝，绝不覆盖。文件恢复必须显式加 `--apply`；目标目录由 `STOREFRONT_MEDIA_DIR` / `STOREFRONT_SUPPORT_DIR` 决定，默认使用 `backend/data/` 下对应目录。
- 数据库与文件归档不是原子快照。需要二者一致时，必须在备份期间暂停相关商城/运营写入；恢复应先在隔离数据库和空文件目录进行，再核对文件与数据库引用后切换。
- ZIP 包含私有客服附件，当前不加密；POSIX 系统限制新归档为当前用户可读写，其他系统沿用目标目录 ACL。请仅使用虚构演示附件，并把归档放在受限、受控的本地目录。此工具不是生产级加密、多实例或异地备份方案。
- ZIP 清单只校验归档中的文件完整性，不会证明文件与恢复后的数据库引用相互匹配。正式环境仍须增加加密存储、同步快照、访问审计、保留策略及恢复演练。
