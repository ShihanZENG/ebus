# 收款凭据与核对设计

## 意图

让订单收款记录可区分模拟与真实数据，保留平台手续费和凭据，并要求真实收款经人工核对后才进入正式已收款金额。这样可避免把演示数据或仅上传、尚未核验的凭据当成真实到账。

## 目标

- 新记录必须明确是模拟记录或真实记录。
- 真实记录必须附带来源编号、订单币种下的结算毛额和手续费，并上传一份凭据。
- 展示净额 = 毛额 - 手续费；手续费不得为负，也不能大于毛额。
- 真实记录提交后状态为“待人工核对”，只有具备付款写权限的用户可显式确认核对；系统不自动判定凭据真实。
- 模拟记录显著展示“模拟/非真实”，不能进入正式收款总额。
- 上传文件保存在本机后端私有目录，不经静态 URL 暴露；只允许 PDF、PNG、JPG，单文件最大 10 MB。
- 订单详情和付款 API 显示类型、毛额、手续费、净额、凭据元数据及核对状态。

## 非目标

- 不连接 Amazon、银行、支付网关或外部 OCR 服务。
- 不自动审批/核对真实收款，不自动生成平台手续费或汇率。
- 不实现多凭据、批量导入、凭据下载链接分享、支付记录删除/修改或冲销流程。
- 不改变订单币种规则；金额及手续费均使用订单币种。

## 规则与兼容性

- 新增类型为 `simulated` 和 `real`；历史记录标成 `legacy`，不猜测历史真实性。迁移可仅将已知演示记录 `source=SIM-SETTLEMENT-IMP-001` 且备注含“非真实收款凭据”的记录标成 `simulated`。
- `amount` 表示订单币种下归属该订单的结算毛额；`fee_amount` 是同币种平台手续费；`net_amount` 由系统计算为毛额减手续费，表示实际净到账。订单收款进度与退款上限按已核对毛额计算；财务现金到账汇总按已核对净额计算，手续费单独展示，避免把平台费用从订单销售额中重复扣除。
- 真实记录 `reconciliation_status=pending`，模拟记录 `reconciliation_status=not_required`；历史记录保持 `legacy`。
- 订单正式已收款（毛额）只累计已核对真实记录与兼容既有逻辑的历史记录；财务现金净到账汇总对已核对真实记录计 `net_amount`、历史记录按原 `amount` 兼容；模拟和待核对真实记录不计入任一正式汇总。订单详情单独展示模拟/待核对记录，避免隐藏。
- 真实记录确认核对要求凭据存在。拒绝/保持待核对不影响其他付款。
- 上传服务端验证扩展名、MIME 类型、文件签名、大小；文件名由服务端随机生成，不信任客户端文件名。附件 API 要求 `payment_records:read`，并通过订单店铺范围校验。
- 真实付款使用一个 multipart 请求同时提交表单和凭据；付款先以 `evidence_status=staged` 持久化，再原子移动文件并标记 `ready`。进程中断时服务启动恢复已提交的 staged 记录；未被记录引用的随机文件清理。只有 `ready` 且文件大小、SHA-256 匹配时才允许下载或核对。无法跨越数据库与文件系统实现单一物理事务，因此用可恢复状态避免静默确认缺失凭据。
- 写入付款、核对操作记录审计日志；任何校验失败不得产生部分付款或孤立文件。
- 财务汇总分开返回已核对收款手续费与平台费用核验观察额，避免同一笔手续费在两类记录同时存在时被合并重复统计。
- 新增/扩展字段须通过 Alembic 迁移；向后兼容现有付款响应字段。

## 验收场景

1. 新建模拟收款时明确显示模拟标签，不增加正式已收款金额。
2. 新建真实收款缺凭据时失败；不匹配币种、负手续费、手续费大于毛额或超限/伪装文件时拒绝。
3. 合法真实收款保存为待核对，订单正式已收款金额和财务净到账金额暂不增加；凭据只对有订单范围权限的用户可读。
4. 具备付款写权限的用户核对后，真实毛额进入订单收款进度、净额进入财务到账统计，手续费可见；重复核对明确拒绝。
5. 现有普通历史付款继续兼容并标明“历史未分类”；已知那条模拟演示记录能识别为模拟。
6. 前端订单详情能填写模式、毛额、手续费、真实来源编号与附件，并展示待核对/模拟/历史标签和计算净额。

## 实现选择（本设计的默认决策）

- 凭据支持 PDF、PNG、JPG；上传大小上限 10 MiB。
- 首次仅支持一条真实记录上传一个附件；金额小数精度 2 位。
- 真实付款通过一个 multipart API 原子提交凭据及收款信息；模拟/历史记录继续使用 JSON API。
- 核对操作沿用 `payment_records:write` 权限；使用独立确认操作与显式审计事件。
- 暂不增加单独的全局财务对账页面；在订单详情完成最小核对闭环。
