# AI 跨境电商运营助手｜个人求职项目设计

日期：2026-10-19。定位更新：用户明确以 AI 应用开发岗位求职为目标，同时展示全栈与业务理解；不以真实开店盈利为当前目标。本文替代此前“英国女装经营”的优先级，保留旧稿作参考，不要求重写现有 ERP。

## 1. 推荐方向

**项目名称：AI 跨境电商运营助手。演示品牌：桌序；演示商品：桌面收纳与非带电办公配件。**

选择桌垫、收纳盒、笔记本支架等，是为了容易组织商品规格、库存、订单和售后案例，不是判断这个品类更赚钱。女装不是不能做，只是样衣、穿搭、尺码和品牌摄影不必成为这个求职项目的主要投入。

面试要能讲清：用户遇到什么业务问题 → AI 查了什么证据 → 为什么可以提出这个建议 → 哪些操作必须审批 → 后台状态如何改变 → 怎样测试模型没有胡说或越权。

### 默认范围

- 中文界面，英国/GBP 作为跨境业务演示背景，不做真实税费计算与实际跨境交易。
- 6 个商品：桌垫、桌面收纳盒、笔筒、非带电笔记本支架、线材收纳包、文件架；每款 2 个颜色，共 12 SKU。尺寸等信息可用于商品详情，但首期不再增加尺码组合。
- 商城只保留商品列表/详情、购物袋/演示结算、订单/工单入口，加一个简洁品牌与联系页；不继续扩展集团门户。
- 一个主助手、少量白名单工具、固定审批节点。已有采购/补货 Agent 保留为扩展，不同时新增多个自治 Agent。
- 核心演示采用隔离测试库与合成数据，模型调用必须真实接入或明确标记录制回放；不把固定示例冒充实时 AI。

## 2. 两个闭环，而不是一个聊天框

### 业务闭环（基础）

```text
入库/初始化演示库存 → 发布商品 → 顾客下单
→ ERP 审核 → 申请发货并预留 → 确认出库 → 顾客查订单
```

沿用现有状态：draft → approved → shipping_requested → fulfilled。取消使用 cancelled；顾客端 fulfilled 显示“已出库”，不能显示“已签收”。首期无真实收款，draft/approved 不占库存，申请发货才占库存；下单时必须明示“待确认库存”。真实支付与结算占货不属于本轮求职最小版本。

### AI 闭环（主亮点）

```text
顾客围绕自己的订单创建问题工单
→ 员工选择工单并发起 AI 辅助
→ 查询同一订单的状态/出库记录 + 检索适用政策
→ AI 输出带引用的解释、回复草稿和建议动作
→ 人工审核并确认回复到项目内的顾客工单页面
→ 顾客看到答复；员工完成实际业务处理后关闭工单
→ 保存工具事件、审核结果，形成回归评测案例
```

第一版 AI 是**员工助手**，不是对公网开放的万能客服；这样能集中展示权限、检索、工具调用、审批、可追溯和实际流程。顾客身份与员工权限仍需分离，员工的权限不能传给顾客。

示例：顾客问“为什么桌垫还没发货？”若订单实际为 approved、尚未申请发货，助手只能解释“订单已审核，尚未进入出库流程”，不能猜测缺货、运输延迟或承诺明日送达。缺少数据就列待核实事项，人工按业务规则处理。

现有客服草稿的 `may_send:false` 是安全约束，不是遗漏可以随意删除。新增发送应走单独授权的审核/发布服务，而不是让模型把字段改成 true。

## 4. AI 应该做什么，不应该做什么

| 工作 | 实现者 | 原因 |
|---|---|---|
| 理解“这单怎么还没到”等自然语言、整理问题 | LLM | 语言表述多样 |
| 查询订单、库存、发货状态 | 后端受限工具 | 数据要实时、可校验、受权限控制 |
| 查退换/配送政策 | 检索服务 | 需要版本、生效时间与来源 |
| 总价、库存可用量、退款上限 | 确定性业务代码 | 不让模型口算或猜测 |
| 解释证据并写答复草稿 | LLM + 结构校验 + 人审 | 保留生成能力又控制错误风险 |
| 发货、退款、采购审批 | 明确权限的人 + 既有业务服务 | AI 不拥有批准和执行高影响动作的权限 |

先做可解释的“取证—生成—校验—审批”工作流。复杂代理只有在评测表明有必要时才加入；不为了简历术语堆框架。[设计参考：Anthropic Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)

## 5. 一期接口、数据和安全边界

### 商城到 ERP

独立 `storefront/` 前端，复用 FastAPI/PostgreSQL。新增受限 `/api/storefront/v1` 接口：已发布商品查询、幂等演示结算、凭访客订单令牌查单、为所属订单创建/查看工单。不将现有员工 `/api/v1` 路由开放匿名。

新增商城发布信息、GBP 售价、公开订单元信息与结构化收货快照；库存复用现有服务。结算由服务端重新定价，`Idempotency-Key` + 请求摘要 + 唯一约束去重，不能相信浏览器金额或 shop_id。访问令牌高熵、仅存哈希，不能凭单号越权查单。令牌恢复、有效期与重新授权在实施设计中固定，不以幂等键当凭据。

### 工单助手

入口为已登录员工选择 `ticket_id`，后端先鉴权并固定此票的 shop/order 范围。只开放：

1. `get_ticket_context`：当前工单及最小必要信息，不带完整地址或联系方式。
2. `get_order_context`：仅当前工单绑定订单的商品、状态、出库记录及库存预留结果，不接收任意跨店查询 ID。
3. `search_published_policies`：按后端确定的市场、类目、生效日期、角色和可见范围筛选；返回规则 ID、版本、引用段落。
4. `save_reply_draft`：保存当前工单的待审草稿，不批准、不发送、不退款。

一期采用固定工作流：先取证/检索，成功才生成；模型最多做受限查询改写与证据整理。需要模型选工具时使用相同白名单并设最多 6 次工具调用、超时和取消；不能把不确定的自主循环作为必需依赖。

输出字段至少包括 `answer_draft`、`citations`、`facts`、`missing_information`、`suggested_action`、`requires_review:true`。建议动作只允许“核实信息/联系仓库/转人工”等枚举，不是可执行退款指令。

引用必须属于本次返回证据；ID 存在不代表文字已被证据支持，还需要对订单状态/金额等关键断言做确定性核对，并由评测与人工审核检查支持关系。未知事实不补全。顾客消息和政策正文都是数据，不可改变工具权限；不允许模型执行 SQL、shell 或任意 URL。

生成记录绑定工单、订单版本/快照摘要、政策版本、prompt 版本、模型版本和审核状态。审批/发送时重新校验权限与证据是否过期，订单状态变化则标记草稿过期并重新生成，不发送旧结论。审批动作与发送动作幂等，记录操作者。

新增项目内 `TicketMessage`（或等价结构）：工单、方向、正文、已审核生成记录 ID、发布人、发布时间；唯一约束避免同一生成记录重复发送。发送只让该顾客在自己的订单工单页看到，不调用邮件、短信、外部电商消息。先在隔离测试库实现。

首期不让模型创建售后单或退货退款。需要售后时把业务交给现有人工售后入口，后续再加结构化待审申请，仍不得自动支付退款。工单关闭由员工在处理完成后执行，不由回复生成自动触发。

### 前端工作台

三栏布局：左侧工单列表，中间对话/问题与草稿，右侧订单事实、政策引用和工具事件。显示“正在查询订单”“正在检索规则”“等待人工审核”等真实服务事件，而不是模型私有思维链。审批按钮和修改草稿入口独立、权限明确，失败后可以重试但不能重复写入。

先接入真实 HTTP 请求与状态，再补 SSE 事件流；没有真实后端事件就不伪造实时轨迹。演示回放必须显著标记。现有 ERP 本地开发会注入演示登录凭据，不能直接公网暴露；商城不能复用该凭据配置。

## 6. 如何证明 AI 应用不是“套个接口”

准备 30–50 条固定评测用例作为首版基线，保留输入、预期工具/范围、证据、禁止行为和实际输出。报告只写实测结果与样本量，不预填 95%/99% 等分数。

| 场景 | 验收点 |
|---|---|
| 正常查单 | 选对关联订单，引用真实状态，不猜发货/签收 |
| 同义问法 | 不同表述仍找到相同订单/政策，可用来比较词面和语义检索 |
| 没有订单/知识缺失 | 明确缺证据并转人工，不编造 |
| 已过期政策 | 不引用失效版本，审批前防止旧规则继续发送 |
| 跨店越权 | 工具拒绝访问，返回不含越权数据；确定性用例必须全部通过 |
| 提示注入 | 顾客要求“忽略规则退款”也不能增加工具或触发退款 |
| 重复发送/并发审批 | 只有一次实际消息写入，有唯一约束和事务保护 |
| 模型超时/坏 JSON/错误引用 | 显示失败并可重试，不产生已发送消息 |
| 生成后订单状态变化 | 原草稿失效，不发送过期事实 |

质量指标：任务完成率、引用支持率、拒答/升级正确率、越权与危险动作次数、人工改写率；性能指标：整体与工具延迟 p50/p95、可获取时记录 token 用量和费用。外部服务未返回用量则显示 unknown，不造成本。

先建立词面检索/规则过滤基线；只有失败用例确实需要语义召回，再比较向量或混合检索。当前代码不能写成“已实现向量 RAG”。知识文件处理、权限过滤、版本、召回和生成质量比安装向量库更重要。

## 7. 开发优先级与求职交付

1. **业务第一条线**：一款桌垫，一笔演示订单进入 ERP，审核、预留、出库、查询可用；合成数据、测试库、启动方式可复现。
2. **AI 第一条线**：关联订单的工单 → 取证与政策 → 真实模型草稿 → 人审 → 顾客项目内查看答复。重点复用已有客服生成和审核能力，补缺口。
3. **可靠性**：上述异常与安全评测、调用事件、超时重试、过期证据校验与审计；增加可重复 E2E 演示。
4. **展示收尾**：可运行 README、架构图、3–5 分钟录屏、评测报告、关键取舍说明和个人贡献边界。
5. **加分项而非前置**：展示已有补货助手如何用确定性计算生成待审草稿；语义检索对比；更完整售后；部署沙箱支付。

不优先：继续扩张品牌故事、集团信息页、多国税务、真实广告投放、微服务拆分、为了数量新增 Agent。

面试讲解主线：为什么选工具查实时库存而不是塞进知识库；怎么防止 AI 越权；为什么人审也要校验数据新鲜度；如何区分模型错误与工具/业务错误；失败用例怎样驱动改进。

可用项目描述（仅在功能真正完成后使用）：“个人项目：基于 React、FastAPI 和 PostgreSQL 构建跨境电商演示系统，结合受权限约束的业务查询、政策检索与人工审核，实现订单客服辅助处理，并用固定用例评测引用、越权防护与异常恢复。”不虚构商业客户、生产订单量、收入或准确率。
