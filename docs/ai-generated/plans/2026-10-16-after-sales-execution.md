# 售后执行 Implementation Plan

**Goal:** 在已批准路线第三批中，补足售后上限、线下退款凭据登记、退货验收入库。
**Architecture:** 沿用 FastAPI/SQLAlchemy 与 React/Ant Design；售后单新增可空 JSON 执行凭据，订单行锁串行化同订单操作，复用库存流水。旧 completed 状态仅表示处理完毕，不能推定实际退款或入库。
**Spec:** 用户要求按已确认五批路线连续开发，不逐步等待确认。当前没有支付/平台授权，只做本地记录，不调用外部退款。

## 约束与实现选择

- 不变更独立OMS；不补造旧记录的执行凭据；没有Git仓库，不创建提交。
- 申请金额累计（pending/completed）不超过订单应付；退货数量累计不超过销售数量，拒绝记录释放额度。
- 退款登记必须售后completed、金额大于0、具备after_sales:write及payment_records:write权限；登记整笔申请金额，累计不超过本地收款及订单应付，凭据号必填。一次售后仅能登记一次，重复返回409。
- 退货仅对已发货订单、completed的return售后单执行；要求after_sales:write及inbound_orders:write、店铺和仓库范围。一次验收包含合格/不合格数量，总数等于申请量；按SKU累计不超过销售数量。仅合格品入公共库存，不合格品仅记录，不自动报废或增加可售库存。明确提示公共库存归属。
- 旧售后数据可能超额：执行时再次检查；拒绝状态不允许执行。
